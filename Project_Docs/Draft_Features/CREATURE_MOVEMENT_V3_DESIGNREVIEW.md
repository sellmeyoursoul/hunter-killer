## 4. No shared "stuck" abstraction

C9's own root-cause section names this directly: flee latch, pursuit-detour latch, and (implicitly) any future goal-specific latch each lack an exit condition for "I've tried every option this mechanism offers and I'm still stuck." Flee and pursuit-detour each grew independent, differently-tuned give-up mechanisms (`flee_give_up_reach_frac`, `pursuit_detour_escalation_count`, different latch-tick counts) rather than sharing one. Explore mode's `boundary_scan` is the only goal with this solved cleanly.

<<Question: Worth extracting a shared "stuck detector" primitive now (before Fight/Mate need their own), or is it cheap enough to keep bespoke-per-goal given how differently each latch's failure mode looks?>>

**Answer (2026-08-28):** Build it, as part of V3 before moving on to other features.

**Design direction, from reading the three existing latches (`_maintain_flee_latch`/`flee_waypoint_ticks_remaining`, `_try_maintain_pursuit_detour_latch`/`pursuit_detour_escalation_count`, `_maintain_explore_latch`/`boundary_scan_turns`):**

All three share the same *mechanical lifecycle* — hold a target + countdown, re-affirm it each tick while valid, count escalation attempts against a cap, clear and fall through to a fresh mint once the cap is hit. That lifecycle (hold/decrement/expire/clear-with-escalation-tier bookkeeping) is what the shared abstraction should own.

What must stay **outside** the abstraction, as goal-specific callables:
- `is_stuck(state, motor_v3) -> bool` — the actual stuck signal differs by physical meaning per goal (flee: reach-fraction vs `flee_dist`; pursuit: detour waypoint still LoS-blocked; explore: bearing/distance-improved progress or fixed turn budget). These aren't parameterizations of one formula.
- `escalate(state, motor_v3, tier) -> Variant` — the next candidate target is also goal-specific (flee's 16-way scan, pursuit's incremental rotation around the last waypoint, explore's tangent walk).

Forcing these two into the shared layer would just relocate the sentinel/resonance-style bugs (§5/§6) into one place that now breaks three goals at once instead of one — so the abstraction should be scoped narrowly to lifecycle bookkeeping, not decision logic.

**Action:** scope as a V3 slice (not deferred to `NEW_GOAL_TEMPLATE.md` guidance-only) — replace the duplicated `*_ticks_remaining`/`*_escalation_count` state fields and duplicated hold/decrement/clear control flow in `_maintain_flee_latch`, `_try_maintain_pursuit_detour_latch`, and `_maintain_explore_latch` with the shared primitive, wiring each goal's existing `is_stuck`/escalation logic in as-is. Land this before Fight/Mate add a 4th latch family.

## 5. Sentinel-value overloading is a recurring smell, not a one-off bug

C9's 7th fix root cause was `Vector3.ZERO` doing double duty as both a "no threat" sentinel and a legitimate world coordinate. GDScript's bare `Vector3`/`float` return types make this easy to reintroduce anywhere a "no value" case exists.

<<Question: Adopt an explicit convention (e.g. a `has_value` out-param, or a wrapper resource) for optional geometric returns project-wide, or fix these one at a time as they're found?>>

**Answer (2026-08-28):** Companion bool per ambiguous field, not a null-based convention.

`state` fields are read into strictly-typed `Vector3` locals everywhere (`var x: Vector3 = state.get("key", Vector3.ZERO)`), which gives compile-time safety on all downstream vector math. Switching the sentinel to `null` would force every one of those ~90 call sites to a `Variant` type plus a manual null-check before any math — a larger blast radius than the bug itself, and it trades a silent-wrong-answer failure mode for null-reference runtime errors wherever a check is missed. Not an improvement.

The companion-bool approach is also not a new convention for this file — `los_blocked_latched`, `boundary_scan_active`, and `flee_give_up_active` already use exactly this shape (a bool as the source of truth alongside a value). Extend it to the ambiguous `Vector3` fields: `flee_waypoint`, `pursuit_detour_waypoint`, `step_goal`, `explore_waypoint`, `shelter_candidate_anchor` — plus `step_ultimate_pos` and `locale_arrival_clear_anchor`, found by the gap-closure pass below (seven fields total; see "Implementation sequencing").

**Important correction to the initial framing:** the bool must be the *only* way validity is checked — not "checked only near `(0,0,0)`." A conditional check that only applies near origin reintroduces the same bug in a new shape (still requires remembering *when* to check). Every existing `== Vector3.ZERO` / `length_squared() < 1e-8` "is this set" idiom (seen at motor_planner.gd:1100, 1577, 1854, 2534, and others) gets replaced outright by reading the paired bool (e.g. `flee_waypoint_set`), unconditionally.

**Action:** scope as a V3 slice alongside §4's latch abstraction (same files, same latch-adjacent fields) — add a companion bool for each of the seven fields, replace every magnitude-based "is this set" check with a bool read, remove the `Vector3.ZERO`-as-sentinel convention from those fields entirely. Exact clear-sites and exit check are enumerated in the "Implementation sequencing" section's gap-closure below.

## 7. Staleness/latency assumptions differ across subsystems reading world state in the same tick

Path-clearance LoS checks have `los_hysteresis_ticks`; threat-awareness LoS checks (feeding goal arbitration) don't — a difference that directly caused one confirmed bug (noted in C9's writeup). This inconsistency isn't called out anywhere as a design principle to audit — it was found incidentally.

<<Question: Worth an audit pass across all per-tick world-state reads (LoS, belief consult, threat sampling) to normalize hysteresis/staleness handling, or fix each inconsistency only as it produces a bug?>>

**Answer (2026-08-31):** Yes — build a single shared per-tick subsystem that all LoS/belief/threat consumers call, rather than fixing inconsistencies piecemeal.

Same rationale as §4's shared "stuck" abstraction: today, path-clearance and threat-awareness each independently decide when a stale LoS read is still trustworthy (one has `los_hysteresis_ticks`, the other doesn't), so bugs like C9's have to be found and fixed per-consumer, and nothing stops a third consumer from reinventing its own (possibly inconsistent) staleness rule. A shared subsystem that samples once per tick and hands back a cached result to every caller makes the hysteresis/staleness policy a single decision instead of N independently-tuned ones.

**Action:** scope as a V3 slice — audit every current per-tick LoS/belief/threat read site (starting with path-clearance's `los_hysteresis_ticks` and the unhysteresed threat-awareness check named in C9's writeup), consolidate them behind one per-tick-cached subsystem, and retire the per-caller staleness logic they currently duplicate.

## Bottom line

The arbitration layer is not where further investment is urgently needed. The waypoint/target-selection layer (flee, pursuit-detour, and the discrete-movement model underlying both) is the concentrated risk, and the pattern across C9/RT1/C16/C17/R1 suggests continued patching has diminishing returns. The highest-leverage open decision is §1's: whether to schedule R1's continuous-controller fallback now, before a third and fourth goal kind (Fight, Mate) inherit the same bearing-only pattern.

## Implementation sequencing (2026-08-31)

Four slices are approved and unstarted: §1 (R1 executor-level continuous controller), §4 (shared "stuck" abstraction), §5 (sentinel-bool convention), §7 (shared per-tick LoS/staleness subsystem). Order:

1. **§5 — sentinel-bool convention**
2. **§7 — shared per-tick LoS/staleness subsystem**
3. **§4 — shared "stuck" abstraction**
4. **§1 — R1 executor-level continuous controller**

**Why this order:** §4's goal-specific `is_stuck`/`escalate` callables will read exactly the fields §5 is fixing (`flee_waypoint`, `pursuit_detour_waypoint`, `explore_waypoint`) and exactly the LoS signal §7 is consolidating (pursuit-detour's `is_stuck` is "still LoS-blocked"). Landing §5 and §7 first means §4 is written once, against the final interfaces, instead of being built against the old sentinel/per-caller-hysteresis idiom and then retrofitted. §5 goes before §7 only because it's the smaller, more contained change (one file, `motor_planner.gd`) — order between §5 and §7 is otherwise not load-bearing and they could be done in parallel if useful. §1 goes last: it's the largest, riskiest rewrite, and it's the direct downstream consumer of whatever `step_goal`/waypoint contract §4 and §5 settle on — building it against a state representation that's about to change (sentinel semantics, latch field names) would mean re-touching `locomotion_executor.gd` a second time.

**§7 — shared per-tick LoS/staleness subsystem — gaps closed (2026-08-31)**

*Classification pass complete.* There are **5-6 distinct per-tick "is X visible" samples** in the motor folder, all routing through the same raw primitive (`AwarenessZone.line_of_sight_clear` → `LineOfSight3D.occlusion_fraction`):

| # | Consumer | File | Checks LoS to | Hysteresis today? |
|---|---|---|---|---|
| 1 | Path clearance | `motor_path_clear.gd` | current `step_goal` | **Yes** — but lives in the *caller* (`motor_planner._latch_los_blocked`), not the LoS layer |
| 2 | Food-plant scan | `awareness_zone_scan.gd` | each candidate food plant | None |
| 3 | Prey/food-creature scan | `awareness_zone_scan.gd` | each candidate prey | None |
| 4 | Hostile-threat scan | `awareness_zone_scan.gd` | each candidate threat | None |
| 5 | Explore wedge probes | `motor_explore_seek.gd` (`_nav_clearance`) | synthetic bearing endpoints, not real objects | None (has unrelated spatial smoothing instead) |
| 6 | Ghost projection | `occluded_in_zone_ghost.gd` | remembered belief positions | A *different* mechanism — belief-ghost time-horizon fade, not tick-hysteresis |

The motivating bug (CLEANUP C11) is consumer #4: a threat near the awareness-cone edge "blinks in and out of `threat_samples` purely on facing," causing goal-hub flip-flop between `avoid_hostiles`/`find_food`. It's currently patched by consumer #6 (ghost projection) as a workaround — a parallel fix for the same disease this slice is meant to cure at the source. No C9/C16/RT1 references exist anywhere under `creature/motor/` — this bug class is specific to the awareness-scan/goal-hub interaction, not the flee-waypoint family.

*Subsystem location decided.* Extend `awareness_zone.gd` (it already owns the raw sampler `line_of_sight_clear`) rather than creating a new file — keeps the primitive and its cache together.

*Cache key decided.* `_latch_los_blocked`'s existing pattern (one bool + one streak counter per creature `state`) only works because path-clearance ever tracks *one* target at a time. Threat/food/prey scanning evaluates multiple candidates per tick, each needing its own independent hysteresis streak. The cache key must be **(creature, target instance_id)** — a dict of streaks keyed by instance_id — not a single latched bool. This is a real change from the existing pattern, not a drop-in reuse of `_latch_los_blocked`.

*Hysteresis tuning decided.* Reuse the existing default (`los_hysteresis_ticks` = 3) for threat-awareness rather than inventing a new default with no evidence behind it, but expose it under its own `motor_v3` key (not shared with path-clearance's) so it can diverge later without a second migration.

*Scope for this slice decided:* **narrow — threat scan only** (consumer #4). Build the shared per-target hysteresis cache in `awareness_zone.gd` and migrate only the hostile-threat scan, since it's the one with a confirmed bug and an existing workaround to eventually retire. **Continuous-controller model — pinned (2026-09-02).** Two independent continuous control laws evaluated every tick, replacing the discrete `TURN_LEFT`/`TURN_RIGHT`/`MOVE_FORWARD` alternation and the `move_blend_max_error_deg` hard gate:

- **Turn:** proportional toward heading error, capped at a max angular rate (deg/sec) — `turn_increment_deg`'s role changes from "rotation applied this tick" to a rate constant. Small errors settle in one tick instead of overshoot-correcting in fixed steps; large errors turn at the cap.
- **Forward speed:** `max_speed * max(0.0, cos(heading_error)) * arrival_damping(dist_to_goal)` — `cos(heading_error)` falls straight out of `dot(facing, direction_to_target)` (already computed for the turn law), so it needs no separate hand-tuned curve or threshold. Zero when the target is at/behind 90° off facing, full when directly ahead, tapering near arrival exactly as `_arrival_damping_frac` does today. `move_blend_max_error_deg` is eliminated as a gate, not retuned.

**Explicit design constraint:** forward speed floors at **zero**, it never goes negative. A target behind the creature means the executor turns in place (zero linear speed) until heading error drops enough for forward speed to become nonzero — it never backs into a target just because backward would technically reduce distance faster. Forward and backward must not become interchangeable/distance-minimizing-optimal choices of one symmetric law; backward stays a **separate, discretely-triggered decision** with its own weight (today's sole case: orbit-break after N facing revolutions in `_select_flight_action`/EAT-orbit logic), not a lane the continuous distance-minimization law can ever route through.

**Flagged as future work, not in §1's scope:** `MOVE_BACKWARD` currently uses the same `max_speed` and same calorie cost as `MOVE_FORWARD` (`locomotion_executor._displace_along_facing`, `motor_action.calorie_cost_for`) — no reverse-speed asymmetry exists in the code today, unlike what discussion assumed going in. Now that forward/backward are staying strictly separate decisions rather than symmetric options, there will be more cases where backing up is the right discrete choice (not just orbit-break) — those triggers, and whether backward should move at a different (likely slower) speed/cost than forward, are explicitly deferred to a future slice, alongside the already-deferred combat strafe/independent-facing work (`CREATURE_MOVEMENT_V3.md:2016`).

A wedge the fox had already walked into and confirmed foodless therefore had the exact same near-zero coverage as a wedge it had never been near — both read as maximally "unexplored" (`1 - coverage[i]/max_cov` → 1.0), so nothing distinguished "go check somewhere new" from "go back to the empty spot again," and the dominant `explore_w_open` term (0.45, intentionally the largest weight since CLEANUP C8) didn't discriminate between the two walls either since both are comparably open from mid-playfield. **Fix:** new `creature/motor/visited_path_memory.gd` (`VisitedPathMemory`, mirrors `DeadEndMemory`'s stateless-static-helper-over-a-plain-Array shape) — a per-creature spatial visitation history, goal-agnostic (unlike belief/live-near coverage, "I've been here" doesn't depend on what the creature was looking for). `MemoryAdapter` gained `_visited_marks: Array`, `record_visited_position(pos, now_ms, motor_v3)` (min-spacing-deduped via `visited_path_memory_min_spacing`, default 40 units, so standing still or moving slowly doesn't flood the history), and TTL+cap maintenance (`visited_path_memory_ttl_sec`=90s, `visited_path_memory_max_entries`=64) wired into the existing `maintain_beliefs` per-tick call. `creature_motor_stack.gd`'s `_maintain_memory_beliefs()` now also calls `record_visited_position` every tick using `_body.global_position`. `explore_bearing_coverage` gained `_accumulate_visited_bearing_coverage`, which marks a wedge covered (`explore_w_visited_wedge`, new tunable, default 0.6 — same magnitude class as a coarse belief) whenever a recent visit mark falls within it, applied via `maxf` (capped, not summed) so repeatedly re-walking the same patch can't grow past that ceiling and drown out real food-density signal elsewhere. A wedge that's been walked through now reads as covered even with zero food beliefs, breaking the tie that was pulling the fox back to the same two walls.

**Regression tests added** (tests/run_all.gd): `_test_memory_adapter_explore_bearing_coverage_visited_wedge` (a visited-but-belief-empty wedge scores `explore_w_visited_wedge`, not 0, while an untouched wedge stays exactly 0), `_test_memory_adapter_explore_bearing_coverage_visited_wedge_caps_not_sums` (5 revisits of the same spot still cap at `explore_w_visited_wedge`, don't compound to 5x it), and `_test_visited_path_memory_record_and_maintain` (pure-function coverage of `VisitedPathMemory`'s min-spacing dedup, cap eviction, and TTL eviction). Verified the first two genuinely fail without the fix (temporarily disabled the new accumulator call, confirmed all three `ASSERT:` lines fire, reverted) and pass with it. Full headless suite green (0 assertion failures). A follow-up 3600-tick headless smoke run completed clean; a second run tripped the pre-existing `MOTOR_INVARIANT` airborne/off-floor watchdog ("stuck-under-geometry, C10") — confirmed unrelated to this change (a third run and a stashed-diff baseline run both came back clean; this diff touches no physics/collision code, and C10 is an already-named, pre-existing flake class with its own dedicated detector, not something newly introduced here).

**Not addressed this pass:** why the fox walks the *entire* distance to a wall before reacting, even once close enough that its forward cone should read as blocked. `_nav_clearance`'s open-space probe is evaluated once at explore-mint time against a fixed point `awareness_radius * 0.5` (750 units by default) away — not re-checked as the creature closes the distance — and that reach is set independent of actual playfield size; duel spawns in the logs suggest a playfield half-width well under 750, meaning most explore waypoints may be minted well past the boundary regardless of direction, which would make "walk to a wall" the structurally expected outcome of almost any explore pick rather than a targeting mistake in a specific direction. Flagged for follow-up rather than changed here — retuning `reach`/probe distance against actual playfield scale, or re-checking clearance as the waypoint is approached, touches explore pacing broadly and needs its own sizing pass rather than a same-turn tuning tweak.

**C10 airborne dig-in (2026-09-04) — richer diagnostics added, root cause revised after direct terrain probing.** `_trip_invariant` hard-quits the instant it fires, so the only evidence from the original occurrence was a single tick's snapshot. Added two cheap, always-on diagnostics to `creature_motor_stack.gd`: a 90-tick rolling per-tick trace (`_invariant_trace`: tick/pos/on_floor/action/blocked) included in every invariant trip's dump, and `_airborne_geometry_probe` (up/down raycasts from the trip position, `hit_from_inside = true` matching `line_of_sight.gd`'s convention) specifically for the airborne case.

Re-ran the headless smoke driver in a loop until it reproduced (5th attempt) and got a full trace. **Initial hypothesis (a terrain-mesh collision seam/gap) was wrong** — checked directly with a one-off probe script that loaded the grasslands scene exactly as `main_3d.gd`'s `_mount_grasslands_floor` does (same auto-bake path) and raycast a dense grid across the fall region: full, unbroken collision coverage, a single continuous "Grid" mesh, smooth uniform ~25.6° slope (confirmed via hit normals along the exact fall trajectory, not just a coarse height finite-difference) — well inside `floor_max_angle` (50°, `creature_*_kinematic_3d.tscn`). No seam, no hole, no floor_max_angle rejection.

**Revised finding:** at every trace tick while `on_floor` still read `true` (ticks 1150-1157), the fox's actual Y sat **~1.7-2.0 units above** the terrain-only raycast hit — far past `floor_snap_length` (0.35). That gap is the tell: the fox wasn't standing on the terrain at all, it was standing on something else roughly 2 units tall that the terrain-only probe never saw. `main_3d.gd`'s `_spawn_interior_boulders()` scatters boulders across the *entire* playfield interior via `pick_uniform_fraction` (not just the perimeter), each getting its own `AutoConvexCollision` body (`PlayfieldBounds3D.ensure_obstacle_physics`, a convex hull baked from the boulder's visual mesh) — a plausible ~2-unit-tall object at exactly this kind of location. The trace's shape is consistent with mounting a boulder and walking off its far edge: level ground contact while atop it, then a clean gravity-accelerating fall (confirmed via the increasing per-tick Y-drop, not jitter) down to the real terrain ~1.85 units below, landing just past where the 45-tick watchdog threshold fired.

**Confirmed, root-caused, and fixed (2026-09-05).** Built an isolated physics repro (flat floor + one boulder, raw `move_and_slide` — no AI stack) to test the hypothesis directly rather than rely on stochastic interior-boulder placement: driving a fox body straight into the boulder on **completely flat ground** climbed it to **Y=2.76**, confirming boulders are climbable by ordinary physics, no slope involved. The boulder's raw mesh AABB is ~2.05 units tall, matching the live trace's standoff almost exactly.

**Checked project history before touching anything** (per user request — [CONVERT_TO_3D.md](../Completed_Features/CONVERT_TO_3D.md) and [CREATURE_MOVEMENT_V3_CLEANUP.md](CREATURE_MOVEMENT_V3_CLEANUP.md)'s C10 section) and found this collision shape wasn't arbitrary: boulders used to be raw concave trimesh, which caused a *different*, already-fixed C10 cause — two independently-baked trimeshes (boulder + terrain) meeting at a seam on a slope let a fast-moving capsule tunnel straight through the world. The 2026-08-06 fix switched boulders to a single convex hull specifically because convex-vs-concave collision is far more tunnel-resistant in Jolt, verified 9/10 → 10/10 clean runs at the time. **Reverting to trimesh (the obvious-looking fix) would have undone that verified tunnel-resistance fix.**

**Three "keep it mesh-shaped" attempts were tried and physics-tested, not just angle-mathed, and all three still climbed:**
1. The current single convex hull (`create_convex_shape()`) — its climbable-angle faces (per raw triangle angle vs. `floor_max_angle`=50°) reach almost to the boulder's peak, even though the source mesh's real faces are 82% steep-walled — hull generation smoothed the real faceted rock into much shallower shortcut faces.
2. A **simplified** hull (`create_convex_shape(clean=true, simplify=true)`, 32 points instead of 63) — its raw angle stats looked much better (climbable band back down near the real mesh's), but the physics repro against it still climbed to **Y=2.75**, no improvement.
3. **Convex decomposition** (`MeshInstance3D.create_multiple_convex_collisions`, up to 12 hulls) — Godot's V-HACD produced only **1 hull**, because the boulder is genuinely close to convex already (matches the user's own read: "basically just a slightly transformed cube") — nothing to decompose.

**Real mechanism, once isolated:** it's not about any single face's angle. A capsule rolling over the *edge* between two adjacent steep facets gets a smoothed effective contact normal right at that edge, shallow enough to register as floor for a moment, letting it incrementally "roll up" a sequence of steep facets regardless of their individual angles — a `CharacterBody3D`-vs-faceted-convex-mesh interaction in Jolt, not a hull-fidelity problem. No amount of reshaping a multi-faceted convex mesh collision fixes this; a smooth, edge-free surface is required to stop it, which is fundamentally not achievable with any convex approximation *of this particular mesh's faceting*.

**Fix — additive second collision shape, not a replacement (user's proposal: "can we put more than one physics object in a 3d mesh?" — yes, `StaticBody3D` treats multiple `CollisionShape3D` children as a union):** `static_obstacle_collision.gd` gained `climbable_lip_top_world_y(visual_root, floor_max_angle_deg)` — walks the real visual mesh's triangles and finds the highest world Y at which an upward-facing face is still within `floor_max_angle` of vertical, i.e. the true boundary (per actual geometry, not a guess) between "genuinely climbable lip" and "too steep." `add_climb_guard_shape(blocker, visual_root, floor_max_angle_deg)` then adds a smooth `CylinderShape3D` (radius/height/position all derived from the mesh's own AABB and that lip height, no hardcoded per-asset numbers) starting just above the lip and extending past the mesh's peak — a smooth cylindrical side has no facet edge to roll over, so it reads as a flat wall for its entire height regardless of the source mesh's faceting. Wired into `PlayfieldBounds3D.ensure_obstacle_physics` right after the existing convex-hull bake. The hull itself is completely untouched — same shape, same tunnel-resistance property from CLEANUP C10, still governs the real base lip and everything else (LoS, obstacle avoidance, navmesh baking) that reads the boulder's collision.

**Verified against the real `ensure_obstacle_physics` code path** (not a synthetic test shape): 5 approach angles into the boulder on flat ground all capped at `max_y≈1.78` (vs. the unfixed climb to 2.76) with zero airborne ticks and zero tunneling. A flat/fully-climbable-angle test mesh (a plane) correctly gets **no** guard at all — genuinely slope-shaped props stay fully climbable end to end, matching the user's explicit preference for keeping legitimate slopes/small steps climbable.

**First version of the fix was incomplete — caught by re-running the actual smoke driver, not just the isolated flat-floor repro.** `CylinderShape3D` has a flat top cap; sized exactly to the mesh's real peak height, a creature could climb the still-present real base lip up onto the guard's own flat cap and walk off *that* edge — the identical climb-then-fall pattern one level down (peak Y ~1.9 instead of ~2.76, still 46+ airborne ticks, same watchdog). Fixed by giving the cylinder generous headroom (`max(radius * 4.0, 2.0)`) above the mesh's real peak so its cap is never reachable from below — invisible collision extending into open air above the rock costs nothing in this ground-only game. Re-verified: 15/15 clean 3600-tick headless smoke runs post-fix, against a pre-fix baseline that was tripping roughly 1-in-5 to 1-in-6.

**Superseded same day (2026-09-05) — climb-guard reverted in favor of scaling the boulder itself.** Project context: movement/memory/goal dev is deliberately ground-only for now to keep testing simple, but the game is headed toward full 3D with climbing as a real, desired mechanic (species/trait-gated slope tolerance — a spider-like creature scaling what a fox can't) — so an invented invisible collision shape whose only purpose is "don't let anyone climb this" cuts against where the physics model is headed, even though it worked. User's alternative hypothesis: the climb exploit depends on the *ratio* of the (fixed-size) creature capsule to the mesh's facet size, not pure face-angle math — since face angles are scale-invariant but that ratio isn't, scaling the boulder mesh up should raise the capsule-edge-rounding threshold without inventing any new shape.

Tested directly before committing to it: same isolated flat-floor physics repro, three configurations —
1. Plain convex hull, native scale (1x): climbs to **Y=2.76** (the original bug).
2. Plain convex hull, **3x scale, no climb-guard at all**: caps at **Y=1.76** — deflects around the boulder instead of climbing it. Confirms the ratio hypothesis directly.
3. Climb-guard cylinder at 3x scale: same result as (2) — the guard is now provably redundant once the boulder is scaled up.

Since (2) alone matches (3)'s outcome with zero invented geometry, reverted `static_obstacle_collision.gd` to its pre-climb-guard state (byte-identical to before this investigation started — `climbable_lip_top_world_y`/`add_climb_guard_shape` and their helpers removed) and `playfield_bounds_3d.gd`'s `ensure_obstacle_physics` back to just the plain convex-hull bake. New `PlayfieldBounds3D.BOULDER_VISUAL_SCALE` (3.0) constant applied at both boulder spawn sites — `main_3d.gd`'s `_spawn_interior_boulders` and `playfield_perimeter_boulders.gd`'s `_spawn_one` — via `rock.scale = Vector3.ONE * BOULDER_VISUAL_SCALE` right after instantiation, before collision bake, so the baked hull reflects the scaled-up mesh. Keeps the mesh as the sole physics boundary (no per-obstacle invented shape), consistent with the ground-only-for-now / full-3D-climbing-later direction — climbing itself stays a live gameplay question for later, this only makes today's boulders read as landmark-scale hard obstacles rather than accidentally-climbable rubble.

**Regression tests updated to match:** removed the climb-guard-specific tests; `_test_boulder_obstacle_collision_bake` reverted to its pre-investigation form (convex-not-trimesh assertion only); added `_test_interior_boulder_spawn_scale` — confirms `BOULDER_VISUAL_SCALE` actually changes the boulder's real mesh AABB (not a cosmetic no-op) and that a scaled boulder still bakes convex, not trimesh, collision (keeps the tunnel-resistance property). Full headless suite green (0 assertion failures) both immediately after the revert and after the scale change. Re-verified against the live smoke driver: 15/15 clean 3600-tick runs (1 from the climb-guard verification pass, 6+ more post-revert, all clean, wall-clock-limited rather than a failure cutoff) — no regression from either the revert or the scale change.

**Regression tests added** (tests/run_all.gd): extended `_test_boulder_obstacle_collision_bake` to assert a `ClimbGuard` cylinder is present after the bake (verified to genuinely fail without the fix — temporarily disabled the `add_climb_guard_shape` call, confirmed the assertion fires, reverted); `_test_static_obstacle_collision_climb_guard_lip_height` (the derived lip sits strictly below the boulder's peak and the guard covers more than half its height — the dome, not a sliver); `_test_static_obstacle_collision_climb_guard_skips_fully_climbable_mesh` (a flat plane mesh gets no guard). Full headless suite green (0 assertion failures).

**Deliberately deferred, tracked in [ENHANCEMENT_BACKLOG_PLAN.md](../ENHANCEMENT_BACKLOG_PLAN.md)** under a new "Falling & vertical traversal" section: (1) falling itself has no defined game-facing behavior yet (no damage, no terminal velocity, no landing recovery) — this fix only stops the *unintended* climb, it doesn't touch what happens when a creature legitimately falls off a real edge, which the user is fine with as a mechanic once it exists; (2) climbing-as-a-skill (species/trait-gated slope tolerance, e.g. a spider-like creature scaling what a fox can't) is explicit future direction, distinct from these per-obstacle hard-stop guards which exist to cap *unintended* climbing for every creature uniformly; (3) the guard's derivation has only been checked against this one boulder mesh — worth a pass once more obstacle variety ships.

## 9. Turn rate should be a per-creature (dexterity-derived) trait, and should govern boundary-scan/eat-orbit too, not just goal-directed movement

**Trigger:** live smoke testing (2026-09-15) caught a rabbit whipping ~149° to re-face a newly-detected live food target in ~6 ticks (`motor_explore_tick.log`, `err=+148.7→+0.3` over ticks t=1679-1686) — structurally correct per §1's pinned model (turn-in-place, `cos(heading_error)` floors forward speed near zero, no clipping through geometry), but visually reads as an unrealistically fast spin. Root cause: `move_turn_rate_deg_per_sec` defaults to a flat **1350°/sec** for every creature ([game_config_merge.gd:374](../../AI_int_lib/game_config_merge.gd#L374)) — chosen at §1 implementation time specifically to *numerically match* `turn_increment_deg`'s old per-tick cap (22.5° × 60Hz), not tuned for how a turn should look/feel.

**A second, independent question surfaced investigating this:** §1's own bucket audit (substep "Bucket re-audit against the pinned model" above) explicitly scoped `turn_increment_deg` as **dual-purpose** and deliberately left one purpose untouched — *"Pure-orientation stepping (`_boundary_scan_turn_budget`, `_pick_boundary_scan_sign`, `_pick_shorter_arc_turn_sign`)... discrete turn-only behaviors... stay entirely out of §1's scope."* That boundary was correct for §1's goal (fix goal-directed movement's overshoot/orbit family without an open-ended rewrite), but it means boundary-scan and eat-orbit still turn at a **second, independent, fixed rate** from everything else a creature does — the exact inconsistency a per-creature dexterity trait would otherwise be trying to express.

**Inventory of `turn_increment_deg` consumers, by how they use it** (grepped across `motor_planner.gd`/`locomotion_executor.gd`):
1. **Tick-budget arithmetic** — `_boundary_scan_turn_budget` (`ceil(360/turn_deg)`) treats the constant as a **tick count**, not a degree quantity; feeds `_boundary_scan_action`'s give-up threshold and `dead_end_record_min_blocked_ticks`.
2. **Turn-direction sign pickers** — `_pick_shorter_arc_turn_sign`, `_pick_align_turn_sign`, `_pick_boundary_scan_sign` — simulate one step to choose left/right by sign only; robust to the value changing, no redesign needed.
3. **Alignment-gate tolerance** — `_move_alignment_min_dot`/`_is_facing_aligned_for_move` (`motor_planner.gd:3241-3262`) — uses "one turn increment" as the heading-error tolerance gating path-clearance/LoS checks, independent of the executor's own speed law. §1 confirmed this "survives unchanged" for its scope, but the underlying number it derives from is exactly what's now changing.
4. **Degree accumulator** — `eat_orbit_turn_deg_accumulated` — sums actual per-call turn amounts to detect a completed orbit.

**<<Question>>: Unify boundary-scan/eat-orbit onto the same continuous rate law goal-directed movement already uses (retiring `turn_increment_deg`'s fixed-step meaning entirely), or keep two independently-tuned turn mechanisms and just add a second per-creature rate for the discrete one?**

**Answer (2026-09-15):** Unify — (b) from the discussion that led here. Boundary-scan and eat-orbit move onto the same rate-based turn law as goal-directed movement, sourced from one per-creature turn-rate value rather than each mechanism carrying its own fixed constant. Rationale: keeping two systems means every future tuning pass (dexterity included) has to reason about two independently-calibrated turn speeds per creature, and the only reason they're currently split is that §1 deliberately scoped discrete turn-only behaviors out to keep that slice's blast radius contained — not because there's a real design reason boundary-scan should turn at a different rate than travel movement.

**Answer (2026-09-15) — rate source:** Derive the per-creature turn rate from `dexterity` rather than a flat config constant. `dexterity` is already named in [CREATURE_ATTRIBUTES_USAGE.md](../Definitive_Features/CREATURE_ATTRIBUTES_USAGE.md) (§ dexterity row) as **Reserved**, with "forced-turn responsiveness" explicitly listed as an anticipated future hook — this isn't a new stat being invented for this purpose, it's activating one already earmarked for it. Whether it trades against `speed` (so a fast-straight-line creature can be a poor corner-cutter and vice versa) is not pinned yet — deferred to the implementation slice.

**Answer (2026-09-15) — curve, pegged values.** Wanted the same growth *shape* used elsewhere for stats: vast improvement stat 1→10, still-noticeable 11→25, significantly smaller but never-plateauing gains 26+. Checked both curves already live in the codebase before picking one ([CREATURE_ATTRIBUTES_USAGE.md](../Definitive_Features/CREATURE_ATTRIBUTES_USAGE.md) §3.4/§3.5 validation):

- `CreatureStatCurve.saturating` (`creature/creature_stat_curve.gd`) — the project's existing general-purpose single-anchor stat→multiplier curve (Composure's WAIT discount, Observation's prey-race giveaway both use it). **Ruled out for this case**: it's a one-pinned-point formula (anchor stat/value, plus implicit 0 and 1.0 asymptotes). Solving it against our three targets showed it can satisfy at most two of {1, 10, 25} exactly before it needs a non-zero floor as dexterity→0 to hit the third — which fights the "starts low, huge early gains" shape being asked for. Stays the right default for the more common single-pinned-value case (documented as such in its own docstring now).
- `StatMath.stat_to_point`'s 1-25 table (`creature/stat_math.gd`) — **used instead**, not for pool sizing but reusing its own relative growth ratios as a proportional shape template, remapped onto turn-rate's chosen range. This is the multi-peg case its table shape is naturally suited to.

**Pegs, anchored on `move_turn_rate_deg_per_sec`'s existing flat default (1350°/sec)** — kept at dexterity 25 unchanged, since it's the exact value that passed every C9/C1-C5 live-repro acceptance leg in §1; nothing needs re-validating against a faster ceiling:

| Dexterity | Turn rate (deg/sec) | Derivation |
|---|---|---|
| 1 | 183.7 | `1350 / (T[25]/T[10] * T[10]/T[1])` = `1350 / (1.95198 * 3.7645)` |
| 10 | 691.6 | `183.7 * (T[10]/T[1])` = `183.7 * 3.7645` |
| 25 | 1350.0 (exact, preserved) | `691.6 * (T[25]/T[10])` = `691.6 * 1.95198` |

where `T[1]=132.82`, `T[10]=500.00`, `T[25]=975.99` are `StatMath`'s existing table entries. Values for dexterity 2-9 and 11-24 interpolate using each index's own normalized position within the corresponding table segment (`(T[i]-T[1])/(T[10]-T[1])` and `(T[i]-T[10])/(T[25]-T[10])`), not a straight line between the pegs — preserves the table's actual per-step growth curvature, not just its three named endpoints. Dexterity 26+ extrapolates via the same decaying-modifier technique `stat_to_point` already uses beyond 25 (next increment = last table-segment increment, decaying ×0.9 per additional point, converging to a finite-but-never-reached ceiling) — not implemented as a literal call into `stat_to_point` (that function returns *points*, not *degrees*), but the same technique, scaled to this table's own last increment.

**Not yet decided:** whether this belongs as a small reusable helper (e.g. `StatMath.rescale_pegged(stat, pegs: Dictionary) -> float`) or stays inline in the turn-rate consumer — per the project's own stated preference (see §4's bandit-learning discussion: don't build shared abstractions before a 2nd/3rd real consumer needs the same shape), stays inline until another stat-driven scalar actually needs the same multi-peg technique.

**Consequences for the four consumers above, once unified:**
- **#1 (tick-budget arithmetic)** changes shape, not just value: `_boundary_scan_turn_budget` and `dead_end_record_min_blocked_ticks` currently express "how long is a full scan" as a *tick count* derived from a fixed degrees-per-tick constant. Under a continuous, per-creature-variable rate, that has to become a degree/time budget (e.g. accumulate turned degrees each tick, same shape as eat-orbit's own accumulator) rather than a precomputed tick count — this is the same "meaning changes, not just value" class §1's bucket-1 audit already used for `turn_increment_deg` itself.
- **#2 (sign pickers)** unaffected — still only need sign, whatever the rate.
- **#3 (alignment-gate tolerance)** needs its own decision: `_move_alignment_min_dot` currently derives its tolerance from "one turn increment," which stops meaning anything fixed once the rate is per-creature and continuous. Needs a replacement tolerance definition (candidate: a fixed angular tolerance in degrees, decoupled from whatever the turn-rate value is) — not resolved here, flagged for the implementation slice.
- **#4 (eat-orbit accumulator)** is actually the easiest case — it already accumulates real degrees turned per call rather than counting ticks, so it's the shape #1 should be converted *to*, not itself a source of new work — provided both consumers pull their per-tick turn amount from the same rate-law call instead of two different constants.

**Action:** scope as a follow-up implementation slice (not started) — replace boundary-scan/eat-orbit's `_rotate_facing`/`turn_increment_deg` fixed-step call with the same rate-based turn law `_blend_turn_toward` already implements for goal-directed movement; convert `_boundary_scan_turn_budget`/`dead_end_record_min_blocked_ticks` from a tick-count to a degree/time budget; pin the dexterity→turn-rate formula (and its interaction with `speed`, if any); replace `_move_alignment_min_dot`'s derivation with an explicit tolerance decoupled from the rate constant; add regression coverage for boundary-scan/eat-orbit at multiple dexterity values (not just the current single-constant default). Pre-implementation checklist and test plan not yet written — do that before starting, per the same discipline §1 used (test plan before cutover, not test-by-test discovery).

**Implemented (2026-09-15).** All four items landed as one slice — no separate pre-implementation checklist beyond this doc's own consequence-by-consequence audit above, which held up (no surprises found during implementation beyond one deliberate simplification, noted below).

- **`stat_dexterity` added** to `CreatureDefinition` (1-25, default 10), mirroring Composure/Observation's exact stub shape (`max_point_dex()`/`curr_point_dex()` via `StatMath.stat_to_point`, always-full pool — nothing spends dexterity yet).
- **`creature_motor_stack.gd::_refresh_move_turn_rate`** (new, called from `tick()` alongside the composure/observation refreshes): `StatMath.peg_curve(stat_dexterity, 183.7, 691.6, 1350.0)` lerped by `curr_point_dex/max_point_dex`, written to `motor_v3["move_turn_rate_deg_per_sec"]` every tick. **One deliberate asymmetry vs. Composure/Observation**: a body with no `CreatureDefinition` is left **untouched** (early return) rather than degraded to the stat-1 floor — non-creature/test bodies shouldn't silently slow down just because this refresh started running; they keep whatever flat default `game_config_merge.gd` already merged in.
- **`locomotion_executor.gd::_rotate_facing`** gained a `delta` parameter and now turns at `move_turn_rate_deg_per_sec * delta` (proportional, same shape as `_blend_turn_toward`'s clamp) instead of a fixed `turn_increment_deg` step per call — the actual mechanism unifying continuous movement and discrete boundary-scan/EAT-orbit turning onto one rate. `_turn_increment_rad` (the old fixed-step helper) deleted as dead code — nothing calls it anymore.
- **§9's item #1 (tick-budget arithmetic) simplification, not the originally-guessed accumulator rewrite.** The consequence-audit above assumed `_boundary_scan_turn_budget` would need converting to a real-time degree accumulator (mirroring eat-orbit's own `eat_orbit_turn_deg_accumulated`). Turned out unnecessary: since physics runs at a fixed assumed rate (`_ASSUMED_PHYSICS_DELTA = 1/60`, matching how the original `1350 = 22.5 × 60` default was itself derived), the existing tick-*counting* bookkeeping (`state["boundary_scan_turns"] += 1` per turn action, compared against a budget) stays completely unchanged — only `_boundary_scan_turn_budget`'s budget *computation* needed to switch from `ceil(360 / turn_increment_deg)` to `ceil(360 / (move_turn_rate_deg_per_sec * _ASSUMED_PHYSICS_DELTA))`. Lower-risk than a full accumulator conversion, and consistent with §1's own Bucket-2 finding that tick/duration counts are independent of *how* movement executes. `dead_end_record_min_blocked_ticks` (which derives its own budget from `_boundary_scan_turn_budget`) needed no separate change — it already composes on top of the now-corrected budget.
- **§9's item #2 (sign pickers)**: confirmed unaffected as predicted — `_pick_boundary_scan_sign`/`_pick_shorter_arc_turn_sign` keep reading `turn_increment_deg` as a pure sign-probe angle, now explicitly documented as decoupled from actual turn execution (doc comments added at each call site and at the config default).

### Slice candidate surfaced during §9 — learned evasive-turn bias from active-pursuit distance trend

**Sketched (2026-09-15), not scoped, not started. Depends on [CM_V3_MULTI_MOBS.md](CM_V3_MULTI_MOBS.md), a separate investigation spawned from this one** — crediting a turn against *every* currently-closing threat (not just the nearest, per the discussion below) needs more than one live predator to ever actually exercise, and today's duel scene is structurally 1v1 (can't spawn a second predator without code changes). That doc tracks the scene/observability/behavior gaps; work through those before this mechanism is buildable against real multi-predator data.

Raised investigating whether flee already rewards maneuverability as a tactic: it doesn't. `_mint_flee_waypoint`/`_maintain_flee_latch` pick one waypoint (best navmesh-reach + obstacle/backtrack-history scored among 6 candidate bearings, 60° apart) and latch it for `flee_waypoint_latch_ticks` (default 16) before re-minting — dexterity's new turn rate helps a fleeing creature reorient faster at each remint, but nothing biases *which* bearing gets picked toward "turn" over "straight." A predator's own live pursuit, by contrast, already re-targets the prey's exact position every tick (`_apply_live_food_objective`), not periodically — so the pursuer's turn rate is arguably more load-bearing today than the prey's.

**Proposed mechanism:** extend the existing per-species learned-tendency substrate — `KindProfileMemory`/`stimulus_learn_registry`, the same shape already proposed in §4's Candidate B for a bandit over `pursuit_detour_max_escalations` — with a learned left/right-vs-straight bias applied as a bonus term in flee's existing 6-candidate bearing scoring. Not a new learning architecture; a second consumer of one that's already designed (if not yet built).

**Reward signal — three options weighed in discussion, converging on the third:**
1. **Binary escape/caught** — rejected. Sparse, delayed, and confounded by everything (predator speed, terrain, luck) — the same unresolved credit-assignment problem §4 Candidate B already flagged for its own reward signal.
2. **Raw distance-gained per remint** — rejected. Dense, but naively biases toward straight-line flight: running directly away maximizes momentary distance-gain rate in open terrain (turning costs speed during realignment), so this would train the opposite of the intended tactic.
3. **Distance-gained, gated on active pursuit** — current direction. Mirror the predator's own `_track_prey_race_and_maybe_give_up` (tracks best/smallest distance-to-target since a chase armed) on the *prey* side: track distance-to-threat over a rolling window, and only treat a remint's bearing choice as reward-eligible once the threat has been closing for a gate window. The established closing rate becomes the counterfactual baseline (no need to simulate a hypothetical straight-line escape) — credit or discredit each turn by comparing closing-rate before vs. after it, against that baseline.

**Precedent this reuses, not invents:** `_track_prey_race_and_maybe_give_up`'s distance-tracking shape (predator side, would need a prey-side mirror); `KindProfileMemory`/`stimulus_learn_registry`'s EWMA-per-`stimulus_kind_id` learning shape (already live for `nutrition_yield`, already proposed for Candidate B).

**Open questions, worked through one at a time (2026-09-15):**

<<Question: gate window size — how many ticks of established closing before a turn becomes reward-eligible?>>
<<Answer: 16 ticks — matches `flee_waypoint_latch_ticks` exactly, so one gate-check aligns with one remint. A guess like everything else here; tune against real data once built.>>

<<Question: which threat's distance gates the reward when multiple hostiles are in awareness at once?>>
<<Answer: not just the nearest — evaluate every currently-closing threat, not a single "the" threat. Cost is low: `awareness_zone_scan.gd` already iterates every in-awareness threat per tick for danger sampling, so a per-threat distance-trend tracker (small dict keyed by `instance_id`, same shape as §7's `latch_awareness_verdict`) piggybacks on that existing iteration — O(threats-in-awareness), not a real cost concern at this game's scale. One physical turn then produces one reward signal per closing threat that tick — not independent samples (same action, correlated outcomes across observers), but still real data-volume help for a lightweight per-`stimulus_kind_id` EWMA. For bearing *selection* (not just reward attribution): proximity-weighted, but a bearing appeasing several medium threats can beat one that's only great against the single closest — **not designed here**, since it's unverified whether `_flee_objective`'s existing multi-threat aggregation (it already blends `threat_samples` into one "away" bearing) already does something like this. Read that code directly before inventing a second weighting scheme, rather than assuming.>>

<<Question: evaluation window after the turn — how many ticks to measure the after-trend before crediting/discrediting that remint's bearing choice?>>
<<Answer: shorter than the gate window, not equal to it. Using 16 ticks for both would let the evaluation window run into the *next* remint (which fires its own new turn choice at tick 16) — the back half of the "did this turn help" measurement would actually be measuring the next decision's effect, reintroducing the same attribution confound the escape/caught signal had, just at a shorter scale. Starting guess: ~half the gate window (8 ticks) — long enough to read a trend over noise, short enough to resolve before the next remint. Tune as needed, same as the gate window.>>
