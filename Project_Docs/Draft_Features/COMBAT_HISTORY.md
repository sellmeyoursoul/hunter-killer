## 1. Design rationale, by topic

### 1.1 Contact detection — why neither `Area3D` nor collision polling

Original open question: `Area3D` child node on creature template vs. polling `get_slide_collision_count()` results? Area3D is cleaner for radius-based melee but adds a node per creature.

There's already an `Area3D` on the creature template — `MobHitbox`, herbivore-only, wired to `body_entered` in `creature_kinematic_body_3d.gd`. But it's narrow and one-directional: it's the "am I touched by a hostile" trigger that ends the round via the predation clamp. The fox template has no equivalent node — collision layers only, for movement. It's a single-purpose, already-shipped predation trigger that predates this design, not a general bilateral contact-detection mechanism.

Everything actually built for combat positioning is pure `Vector3` math, not physics events: `CombatPositionResolver.resolve_combat_target()`/`positional_modifier()` take plain `attacker_pos`/`opponent_pos` args — distance/arc comparison against `preferred_range`/`preferred_arc_deg`, same pattern every other motor function uses (`cardinal_avoidance.gd`, `seek_planner.gd`). Even `tactic_fight_active` itself was, at the time of this decision, a hardcoded stub in a function that takes nothing but positions and dictionaries, no Nodes. `CLAUDE.md` is explicit: "Motor and vitals logic must be pure (no side effects on Node state) to remain unit-testable headlessly." An `Area3D` node fails that outright; `get_slide_collision_count()` is also Node-coupled (tied to `move_and_slide()`'s per-frame result).

So the option that actually fit the codebase as it stood was a third one neither original option named: plain distance/arc comparison against the action's `preferred_range`/`preferred_arc_deg`, using the same position values already threaded through the motor pipeline every tick — no new node, no collision polling, `MobHitbox` left untouched as the separate predation-trigger mechanism it already is.

### 1.2 Predation / `creature_defeated` interaction — why alongside, not replace

Original open question: what happens to the existing `creature_predation_math.gd` calorie-transfer logic (predator gains calories on kill)? Should `creature_defeated` replace the predation clamp entirely, or run alongside it?

Decision: for now a kill should trigger a win condition, and if more creatures are added to the playfield later, a predator killing its prey should still get the calories. This is all placeholder until objects land, at which point a defeated creature would drop an edible meat object instead of an instant transfer.

Implementation nuance flagged (not a design change): once actions/reactions ship, `creature_defeated` fires from pool depletion (see `COMBAT_RESOLVED.md §4.7`, "Defeat fires when pool hits 0 with no overflow"), not from `MobHitbox`'s current instant-touch trigger — the calorie/win-condition wiring moves to hang off that event instead, same shape, different trigger point.

### 1.3 Feint detection — why deferred beyond wit-vs-wit

Original open question: feint detection formula — wit vs. wit check? Observation modifier? Define when feint action is authored.

Decision: a `stat_wit` vs. `stat_wit` opposed contest, this phase. Exact formula shape (reusing the resolution-formula pattern vs. a simpler opposed-roll check) is left to whenever the definitive feint action is authored — deferred like every other numeric constant in this doc.

### 1.4 Observation-unlock timer — why anchored to memory, not a fresh timer

Original open question: observation-unlock timer — per combat episode or per opponent pair? Resets on disengage/reengage?

Decision: for as long as the target is remembered. `combat_observation_sec` is scoped to the specific opponent's `instance_id` and persists across disengage/reengage with that same opponent — it does not reset just because the current combat episode ends. It expires only when that opponent falls out of memory entirely, i.e. whenever its per-instance awareness-ledger row is evicted/forgotten. The exact eviction rule for that row is one of the ledger's own flagged open dependencies (storage/schema, pending V3/MEMORY sign-off) — this decision just anchors the unlock timer to it rather than inventing a separate, new decay rule.

### 1.5 `relative_threat_mod` — why the species-experience term was removed (the `kind_threat` discovery)

The original draft of `relative_threat_mod` (per explicit design direction: creatures shouldn't be omniscient about an opponent's condition; threat perception should factor relative size, visible danger signs, and experience with that *type* of creature attacking vs. fleeing, plus a `compassion_self_interest` disposition bias) proposed a composite of six inputs, including a new species-keyed `species_aggression_table.gd` tracking attack-vs-flee history per species, reusing the combat-experience-table's evidence-backoff shape and blending toward neutral `0.5` when thin.

That design was confirmed as "a solid start" for playtest/tuning purposes, but a follow-up question — whether filling in V3's `Fight` goal stub would change any of V3's already-resolved goal math (`urgency_dist`, `threat_disposition_mod`, `kind_threat` inside `urgency_flight`) — surfaced a real problem while checking `kind_threat`/`_kind_profile` against `CREATURE_MEMORY.md` §5.7: `_kind_profile` is a **per-creature** (not global) `stimulus_kind_id → facet` map, with a `threat_danger` facet (neutral prior `0.5`, EWMA-updated via `record_observation`) read directly by `urgency_flight`'s own `kind_threat(sample) = kind_profile.facet(threat_danger, sample.stimulus_kind_id)` term — a multiplicative factor that already sits at the top level of `urgency_flight`, sibling to `relative_threat_mod`, not inside it. The proposed `species_aggression_table.gd` would have double-counted the same evidence twice in the same product.

Resolution: no `experience_factor` in the composite, no new table, no new file. `_kind_profile.threat_danger`'s write trigger was already specified as "Flight episode end; near-death tier" but explicitly did not yet cover combat outcomes — combat's actual contribution is extending that trigger list to combat episode end, feeding it the same `effectiveness`/`outcome_score` signal the combat-experience system already computes. This is a write-path extension on existing memory infrastructure, not new combat-owned state, and preserves the same "creatures shouldn't be omniscient" property the original design wanted: a creature that's never had a bad encounter with a kind still reads the neutral `0.5` prior.

This was self-identified during research prompted by a direct question about whether the new design perturbed V3's existing math — not a correction requested after the fact.

### 1.6 `Fight` hub goal — why `urgency_fight` isn't Flight's stack reused

V3's own directive only names `urgency_dist` (proximity) as geometry shared between Flight and Fight — it does not say `Fight` reuses `kind_threat × threat_disposition_mod × relative_threat_mod` wholesale, and there's a real reason it shouldn't: those three multipliers answer "how much should this make me want to *flee*," and for a responder deciding whether to fight back instead, a low `relative_threat_mod` (weak opponent) should arguably *raise* fight-worthiness, not lower it — the opposite sense from Flight.

The proposed inversion: `urgency_fight = clamp(urgency_dist * (1.0 - kind_threat * relative_threat_mod), 0.0, 1.0)`, where the ceiling subtracted from is exactly `1.0` since both `kind_threat` and `relative_threat_mod` are already clamped to `[0,1]` — no separate max-value constant needed. `threat_disposition_mod` was deliberately dropped, not merely omitted for simplicity: it's calibrated specifically as a flee/skittishness scalar (nudged by benign-exposure/hunt-evade events), so it has no fight-relevant meaning to invert. The responder's own risk appetite is already represented on the perception side via `relative_threat_mod`'s `compassion_self_interest` bias — reusing `threat_disposition_mod` here would bolt on a second, mismatched disposition axis rather than restore a missing one.

Scope note: this resolves the responder path only. The aggressor case (a predator's own hunt drive) is a different calculus again, closer to Eat's target-lock than to a threat-response, and remains deferred pending V3's prey-chase/pursuit mechanism (itself explicitly deferred in V3's own doc audit).

### 1.7 Acute fast-path — why generalized from a Flight-specific bypass

V3's own forward-reference already named the shape combat should extend: "attack action triggers fight/flight immediately — planner and frozen goal table do not compete with acute response." The question was whether to author a bespoke "when attacked, evaluate only {Fight, Flight}" carve-out, or treat the fast-path as a *timing* mechanism only.

Resolved on the latter: the acute trigger forces the same full hub `weight` comparison used every ordinary consideration cycle to run immediately (off-cadence) instead of waiting for the next scheduled tick. Fight and Flight are expected to dominate the result in the overwhelming majority of cases because their inputs are large in this situation — not because every other candidate is excluded from being scored. This matters because there are real cases (near-starvation) where eating a shrub could plausibly outweigh fight-or-flight, and V3 already has a hard override (`calorie_ratio < starvation_override_food_ceiling` forcing Eat) that a pure re-eval model needs and gets for free, rather than needing a bespoke carve-out. This also extends the doc's existing "no special combat-ends state machine" philosophy (emergent disengagement, §4.1/§4.7) to *entry* into combat/flight as well, not just exit — one principle for both ends, discovered by generalizing the original narrow question ("what's the impact if it was just an immediate goal re-eval?") rather than accepting the hardcoded 2-goal bypass as given.

Two existing rules (Find shelter's categorical suppression during acute threat; the in-progress-turn-sequence preemption) were kept, with their trigger condition broadened from "Flight fast-path active" to "an acute fast-path trigger is active" — neither needed to be redesigned, just regated.

### 1.8 `MotorContext` retirement discovery — the Bucket A / Bucket B split

While working through the contact-detection question (§1.1 above), it became clear that `MotorContext` — which every `tactic_fight_active` reference in the doc assumed as the carrier — is not being reshaped by V3, it is being retired outright. `CREATURE_MOVEMENT_V3` explicitly deletes "Cardinal / motor code may set `MotorContext` tactic flags," replacing per-tick flag-setting with "planner/hub sets context at outcome time only" (V3 §12.3.4).

Digging in further showed the doc's `tactic_fight_active` references actually bundled two unrelated integration points under one flag name, and only one of them had a V3-side answer:
- **Salient-write use** (memory-write gating at combat episode outcome, one-shot) — V3 resolves this concretely: carrier renamed, flag ids preserved, caller becomes an outcome hook. Called **Bucket A**.
- **Hub urgency / goal-weight use** (live, per-tick, feeding fight/flight goal-weight scoring continuously) — V3 does not resolve this at all. V3's `Fight` hub-goal row is a bare stub ("Not Defined yet... until combat is implemented"), and `relative_threat_mod` is stubbed at `1.0` "pending combat." Called **Bucket B** — the real design work, resolved piece by piece (§1.5–1.7 above and `COMBAT_RESOLVED.md §11`).

Bucket A was deliberately left as a pending mechanical sweep (not executed in isolation) until Bucket B's shape was known, since several sentences in the original doc blended both concerns in one clause (e.g. "tactic_fight_active multiplier from MotorContext" reads as one idea but is actually Bucket B's urgency math and Bucket A's carrier tangled together) — untangling them before Bucket B locked would have forced a second edit pass.

### 1.9 `_goal_belief` rejected as ledger storage — why

The live engagement/threat ledger (per-instance, keyed by `instance_id`) needed a storage home. V3's `_goal_belief` was considered and rejected: that store is a location/value belief for goal-relevant resources (Eat/Shelter), tiered by uncertainty and pruned via LRU + `last_observed_ms` eviction tuned for gracefully forgetting stale, low-stakes sites. Using that eviction policy for authoritative live-engagement state risks a creature's `engaged`/`threat_trigger` entries being silently evicted under memory pressure — a serious bug, not graceful degradation — and the schema shape (location + kind + consumability vs. a live mutual relationship with another agent) doesn't fit either. Recommendation instead: a sibling per-instance store using the same `instance_id`-keying idiom and reusing V3 §8.1's awareness-zone scan to populate it, but not `_goal_belief`'s storage/eviction machinery — flagged as needing sign-off from whoever implements V3's memory adapter, not combat's to decide unilaterally.

### 1.10 Selection-rule / novelty-vs-proven exploration bias — options considered

**Problem:** the combat experience table initializes every `prev_action_id → curr_action_id` pair to a neutral weight of `1.0` and only moves via EMA on pairs actually attempted. A newly unlocked action enters at the same neutral `1.0` as any other untried pair, while an already-reinforced favorite sits above it. Naive argmax selection risks a large action pool permanently starving new options.

| Option | Mechanism | Fit with existing engine pattern | Trade-offs |
|--------|-----------|-----------------------------------|------------|
| **A — Ranked argmax (selected)** | Compute a `combat_rank_score` per candidate (confidence × novelty/proven bias, same shape as `goal_source_memory.gd`'s Slot B `replay_rank_score`); pick the highest-scoring queueable candidate | Direct transplant of a shipped, tested formula; stays pure/deterministic, matching the project convention that motor/selection logic be headlessly unit-testable with golden values | Deterministic: on a genuine tie, or for a Stability-leaning creature whose novelty score never clears the incumbent, a candidate can go unpicked indefinitely — may be *correct* personality expression, but needs an explicit tie-break rule |
| **B — Softmax / weighted-random over rank score** | Convert `combat_rank_score` into a probability distribution and sample | Guarantees nonzero trial probability for every candidate | Breaks from precedent — Slot B is pure ranking, never stochastic sampling. Introduces RNG into a subsystem the project otherwise keeps pure and deterministic; existing golden-value test style would need to become seeded/statistical — a real testing-cost regression |
| **C — Epsilon-greedy bolt-on** | Argmax normally; with probability ε pick uniformly at random | Simple, well-understood bandit pattern | Least reuse — a third exploration paradigm alongside Slot B's lerp and Option A's rank score; needs its own tunable and trait-scaling rule, duplicating work Option A already does via `novelty_score` |

Selected Option A: it answers the starvation concern using a formula already shipped, already trait-aware, and already fitting the codebase's pure-function/headless-test convention. Revisit Option B only if playtesting shows a Stability-leaning creature never tries a candidate even once across its lifetime — a tuning problem to observe first, not a reason to abandon Option A up front. A high-Stability creature persistently avoiding new actions is intended personality expression, not a bug on its face; do not add a stronger forced-exploration mechanism preemptively. If playtesting shows this becomes a real problem, candidates for a targeted fix include a decay term eroding `weight`/`proven_score` over time when a pair goes unused, a wider or `stat_observation`-gated chaos band, or a hard floor forcing at least N trials of any newly-available action.

### 1.11 Pair-level vs. action-level tracking — options considered

**Problem:** pure pair-level `attempt_count`/`success_count` (keyed on the exact `(prev_action_id, curr_action_id)` combination) fragments evidence as the action pool grows — a `curr_action_id` that's genuinely proven overall, but reachable from five different `prev_action_id`s, may never clear the evidence-confidence threshold on any single pair, permanently reading as thin/novel even though the creature has effectively tried it many times. Pure action-level tracking (drop `prev_action_id` from the key entirely) converges fast and sidesteps fragmentation, but throws away the sequence-specific learning that's the entire point of a transition-pair table.

| Option | Mechanism | Trade-offs |
|--------|-----------|------------|
| **A — Pure pair-level (status quo)** | Key strictly on `(prev_action_id, curr_action_id)` | Full sequence specificity; fragments badly as the pool grows |
| **B — Pure action-level** | Drop `prev_action_id`; key on `curr_action_id` only | Scales cleanly, converges fast; loses sequence learning entirely |
| **C — Hierarchical backoff (selected)** | Keep the pair table as source of truth for `weight`/ranking, but maintain a lightweight marginal `curr_action_id → {attempt_count, success_count}` aggregate alongside it; when a pair is thin, blend its evidence/success_rate toward the marginal's, using the pair's own thin-cap as blend weight | Keeps full specificity where data supports it, degrades gracefully where it doesn't; the one genuinely new piece of math in this transplant (standard hierarchical-shrinkage/n-gram-backoff pattern, new to this project though not to statistics generally) |

Selected Option C: it directly answers the scalability concern (marginal table is `O(actions)`, not `O(actions²)`, cheap to maintain incrementally) without losing the sequence-specific signal that motivated a pair table in the first place. `weight` itself stays un-blended — a new pair for an otherwise well-proven action still initializes at flat neutral `1.0`; backoff only affects how much the creature trusts the confidence/novelty read for a thin pair, not the outcome estimate itself.

The opponent-observation table was confirmed to need the same backoff treatment, for a stronger reason than the self-table's: a reaction is queued *before* the opponent's action is known, so reaction selection can never condition on the specific incoming move anyway — the marginal over `own_response_id` is close to the primary decision-relevant signal here, not just a thin-data fallback. The spatial overlay was confirmed exempt — it isn't pair-keyed at all (a flat dict of positional bias keys), so there's no pair-fragmentation problem to back off against; it calls the shared math with its own counts standing in for the marginal, collapsing the backoff lerp to a no-op.

### 1.12 `outcome_score` generalization beyond Resisted Actions

`outcome_score` (feeding `weight`'s EMA) was loosely defined as "damage dealt relative to cost paid." Formalized as `benefit_score - cost_ratio` so the same shape could eventually generalize beyond Resisted Actions, rather than being combat-specific math: `benefit_score` is a domain-specific plug-in (combat's is `effectiveness`), `cost_ratio` is domain-general (reuses the existing `costs: Array` pool-drain pattern — no new fields).

This shape was deliberately generalized past combat because the opponent-observation table's action-id-agnostic design already anticipated non-combat use, and the same cost/benefit tradeoff shows up outside any resisted/opponent context too — e.g. a creature choosing to sprint vs. walk toward a food source: sprinting costs more calories per tick (same pool-drain shape) but may arrive sooner (a `time_to_goal_ratio`-style benefit proxy). Note that "arriving sooner enables visiting a second food source" is a multi-step, downstream benefit that can't be scored at the moment a single action resolves — any future movement `benefit_score` should stick to something measurable immediately, not compound opportunity value, which is a separate credit-assignment problem this formula doesn't solve. Sprint-vs-walk isn't a Resisted Action (no opponent resisting), so this generalization sits outside combat's own scope — `CREATURE_GOAL_DRIVERS.md`'s Slot B has a conceptually equivalent mechanism for goal-pursuit tactics, but `CREATURE_MEMORY.md §14` currently uses a boolean/tiered `reward_scalar` only and explicitly defers magnitude-based reward shaping until after playtest, with a "hybrid" option already anticipated in that doc's own backlog comment.

Decision: hybrid, deferred to combat-implementation time. When Slot B eventually gains cost-awareness, it should be additive — keep the tiered system exactly as-is (driving confidence/counts, unchanged), and add this `outcome_score` shape as a new, parallel EWMA magnitude track that modulates ranking alongside, not instead of, confidence. Deliberately **not** designed or implemented in `CREATURE_GOAL_DRIVERS.md`/`CREATURE_MEMORY.md` as part of this combat design pass, since those docs were active ground for the concurrent V3 motor refactor — this generalization idea should only be picked up as its own implementation step, once V3 has landed, rather than edited speculatively now.

### 1.13 `trait_rank_bias` generalization — spatial overlay worked examples

Combat's `t = (change_stability + 100) / 200` lerp turned out to be a single-axis case of a more general pattern: a primary trait axis sets a base lerp position, and zero or more secondary axes modulate it, gated by how strongly the primary already leans toward its second pole. Generalizing to that shape — rather than writing bespoke math per table every time a new decision needs this bias — lets combat and the spatial overlay share one function and differ only in configuration.

Walking the spatial overlay's four cases (`{primary_axis: "explorer_builder", modifiers: [{axis: "change_stability", strength: spatial_cs_modulation}]}`):
- **Full Explorer** (`explorer_builder = -100`): `base_t = 0`, `gate = 0` → `t = 0` (full novelty) regardless of `change_stability` — an explorer's pull toward covering new ground isn't tempered by stability.
- **Full Builder + full Stability**: `base_t = 1`, `gate = 1`; the modifier pushes further positive but clamps at `1` — the strongest proven/"tried-and-true" bias, matching a high-builder high-stability creature sticking with a known (even suboptimal) location and methods.
- **Full Builder + full Change**: `base_t = 1`, `gate = 1`, `change_stability = -100` → `t = clamp(1 - spatial_cs_modulation, 0, 1)`. With a default like `0.5`, `t` lands near neutral — more proven-leaning than a pure explorer, but genuinely open to new optimization methods or relocating if a fundamentally better spot is found.
- **Neutral `explorer_builder = 0`**: `gate = 0` → `t = 0.5` regardless of `change_stability` — stability alone doesn't move a creature with no explore/build lean.

`community_individual`/`compassion_self_interest` were explicitly left unwired in both configs — the community-axis behavior discussed (biasing toward leaving a location that only meets basic needs with no buffer for others) is a stay/leave resource-margin threshold, not a bias about *how* to engage with a known-vs-new position, so it doesn't belong in this lerp. Both remain available `modifiers` slots for a future decision with an established intuition for them.

### 1.13.d `combat_rank_chaos` — independent tunable, not shared with V3's chaos siblings

Original open question (§10): does `combat_rank_chaos` share the `0.15` default with V3's `blocked_objective_chaos`/`goal_consideration_chaos`, or get tuned independently — and what's the epsilon-band width for "near-tie"?

Decision: independent value, `0.15` only as a tuning starting point, not a shared constant — `combat_rank_score` sits on a different scale than V3's goal-weight chaos siblings, and combat is expected to want more jitter (a larger epsilon band) than ordinary goal selection once tuned. A further idea surfaced during the answer — letting a stat or skill (observation/wit/composure) narrow the band to represent a creature's experience or discipline — was explicitly called out as out of scope for this implementation; logged as a backlog item ([ENHANCEMENT_BACKLOG_PLAN.md](../ENHANCEMENT_BACKLOG_PLAN.md)) rather than designed now.

### 1.13.e `delta_factor` transplant — fast/slow EMA pair instead of a windowed `success_delta`

Original open question (§10): Slot B's `delta_factor` (recent-trend bonus/penalty on `confidence`, driven by a windowed/EWMA `success_delta`) was dropped from the combat transplant because combat's pair table never accumulated an equivalent trend signal — only a single EMA (`weight`) and flat lifetime counts.

First pass at resolving this incorrectly assumed `weight`'s own EMA smoothing already made a separate trend term redundant. Checking `CREATURE_MEMORY.md:728` disproved that: Slot B's `stored_strength` is *also* EMA-blended (`lerp` toward `success_rate` at write, plus per-tick decay) and Slot B still kept `delta_factor` as a distinct signal — the two answer different questions. `weight`/`stored_strength` is "what's my current best estimate," `delta_factor` is "is that estimate trending up or down right now." Two pairs at the same `weight` can be heading in opposite directions, and `confidence` alone can't tell them apart.

This gap matters more for combat than it did for Slot B, which is why it was worth solving rather than permanently omitting: Slot B's world (location/goal replay) is largely static, but combat is explicitly adversarial — an opponent can start reading and countering a previously-effective action mid-fight. Without a trend signal, a pair's flat lifetime `success_rate` doesn't reflect "the last several attempts all failed" until enough of them accumulate, so the creature keeps re-queuing a pattern the opponent has already adapted to for longer than necessary.

Resolution: rather than transplant the windowed-buffer machinery Slot B uses for `success_delta`, add a second, faster-decaying EMA (`fast_weight`, `combat_exp_fast_ema_alpha`) of the same `outcome_score` signal `weight` already tracks. `delta_factor` reads `sign(fast_weight - weight)` instead of a window's trend, folds into `confidence` with the same bounded `±combat_exp_delta_strength` shape as the original. Cost: one new float per tracked value (no window/buffer state), applied uniformly across all three tables (self-experience pair, opponent-observation pair, spatial-overlay bias key) since the mechanism only needs a value's own fast/slow EMA pair — unlike the marginal/backoff mechanism (§1.11), it doesn't care about pair-vs-flat-dict storage shape, so there's no exemption case the way spatial overlay was exempt from backoff.

### 1.14 Overflow-drained pool reads as locked `0`, never blended

Reviewing the split doc set surfaced an ambiguity in §4.2's stat wheel overflow (a pool at 0 pays costs from a neighbor at 2:1): nothing said what a calculation reading the *depleted* pool's own current value should see once overflow is actively covering its costs. Left unstated, an implementer could plausibly read the depleted pool as "not really empty" since play continues past 0 via the neighbor, and blend some fraction of the overflow activity into `pool_scale()`/mitigation/band-lookup reads.

Resolution: overflow is a cost-payment mechanism only. It changes which pool's points get spent; it never changes what the depleted pool's own `curr_point_*` reads as anywhere else in the formulas (§4.4's `pool_scale`, §11.2's condition bands, etc.) — that value stays locked at `0` for the rest of the tick's math, same as a creature with no overflow available at all. A creature queuing Fit-costing actions off a depleted End pool still deals damage at the `pool_scale(0) = 0.25` floor; there's no way to buy back into a higher `curr_scale` band by drawing on a neighbor.

### 1.15 `fight_won` `GoalKind` — resolved

Original open question: should combat define a new pack-extension `GoalKind` (`fight_won`) for the winner's salient write, or map a combat win onto the existing `find_food` `GoalKind` at the kill moment, since the predator did in fact just eat?

Decision: `fight_won`, not `find_food` — it generalizes to non-predation contexts the existing `GoalKind` doesn't (a herbivore driving off a rival isn't "finding food"). A follow-on implication was flagged, not designed: once the meat-drop object system lands (§4.9's existing predation placeholder), "predator ate" stops being a single instant transfer and becomes a chain — find prey → win fight → loot the corpse. `fight_won` is meant to sit as the mid-point `GoalKind` in that chain, and `find_food`'s own process will likely need a matching refinement at that point. That refinement is out of scope now; it's a forward note tied to the already-deferred meat-drop dependency, not new work for this phase.

### 1.16 `stat_will` feeding urgency directly — resolved, formula deferred

Original open question: should `curr_point_will` modify the `avoid_hostiles`/fight urgency weight directly (low will → readier to flee), or does will only act indirectly through §4.7's pool-drain/persistence-threshold framing?

Decision: yes, factor it in directly — confirmed, not just left to the indirect threshold effect. No exact formula was specified as part of the answer, so rather than inventing one unprompted, §11.3 records the qualitative direction (depleting will raises flee urgency / dampens fight urgency) and carries a first-pass candidate — reusing §4.4's existing `pool_scale` curve as a self-urgency multiplier — behind a `<<Comment>>` pending balance-pass sign-off, consistent with how every other unbalanced numeric constant in this doc is handled (§4.6, §11.2).
