### RT1 — Rabbit flees into a terrain dead-end instead of the real exit

**Status:** `done` — root cause confirmed and a scoped fix shipped in `_mint_flee_waypoint` (see below); the deeper "optimal escape near a genuine corner" problem is not solved and remains R1 architecture-risk territory ([CREATURE_MOVEMENT_V3_CLEANUP.md](CREATURE_MOVEMENT_V3_CLEANUP.md) R1), not reopened here.

**Repro:** Duel spawn landed the rabbit in a valley (steep walls on most sides, real exit to the east) with the fox approaching from the east. On sighting the fox, the rabbit fled *deeper into the valley* (a dead end) instead of toward the one real exit. Note: at the time of this repro, `main_3d.gd`'s `_DEBUG_FORCE_EDGE_CHASE_SPAWN` debug flag was still `true`, which pins the duel pair to fixed fractions (herb `(0.05, 0.5)`, carn `(0.20, 0.5)`) on every run — so this exact terrain/duel arrangement is deterministic today, not something the new randomizer produced by chance. Locked layout: `spawn_layout_locked_rt1.json` (copied from `spawn_layout_last_run.json`), seed `900425302035824835` — point `playfield_spawn.locked_layout_path` at it to replay (though since the debug flag currently overrides duel-pair placement regardless, the lock mainly pins interior boulder/food placement for this repro, not the duel pair fractions).

**Investigated:**
- **Dead-end awareness:** `DeadEndMemory` / `MemoryAdapter.is_waypoint_dead_end` (`creature/motor/dead_end_memory.gd`, `creature/motor/memory_adapter.gd:200-221`) is wired only into explore/find-food step-objective code (`motor_planner.gd:1707-1708,2431-2432`, `motor_explore_seek.gd:40-41,61-62`). `_mint_flee_waypoint` / `_flee_objective` / `_flee_candidate_reach` (`motor_planner.gd:1810-1976`) never consult it. **The rabbit has zero dead-end awareness while fleeing** — confirmed, not a weight-tuning gap but a missing signal entirely.
- **Flee candidate scoring:** `_mint_flee_waypoint`'s 6-candidate sweep (60° apart, `motor_planner.gd:1920-1934`) and its 16-direction give-up escalation (`:1946-1960`) both score a bearing *only* via `_flee_candidate_reach` (`:1810-1822`) — `NavigationServer3D.map_get_path(map_rid, creature_pos, creature_pos + dir * flee_dist, true)`, scored purely by how far that one-shot path reaches. `flee_dist` itself is `awareness_radius * 0.5` (`_flee_objective`, `:2041`) — with `awareness_radius` defaulting large (~1500 in the legacy spine), `flee_dist` is effectively "as far as the navmesh lets you go," so in practice this scores each bearing by **local open room before hitting geometry**, not by whether the bearing eventually reconnects to the rest of the map. No elevation/slope term (`PlayfieldGroundSampler`/`sample_elevation`/`local_depression_score` have **zero callers** in `motor_planner.gd` or `creature_motor_stack.gd` — elevation awareness is spawn-time-only, per [ENVIRONMENT_MODEL_PLAN.md §6.4](../Definitive_Features/ENVIRONMENT_MODEL_PLAN.md)). `weight_edge`/`weight_obstacle` (`AI_int_lib/game_config_merge.gd`) feed general steering cost, not `_mint_flee_waypoint`'s candidate selection. **There is no mistuned weight to retune here — the signal needed to distinguish "roomy dead end" from "narrower real exit" simply doesn't exist yet.**
- **Relation to C9:** confirmed same mechanism the user guessed — `_mint_flee_waypoint`'s reach-based scan *is* C9's 5th/6th-fix machinery ([CREATURE_MOVEMENT_V3_CLEANUP.md](CREATURE_MOVEMENT_V3_CLEANUP.md) C9). That doc's own history already names this exact blind spot as unresolved. This is a new *manifestation* of the same underlying "reach-only, connectivity-blind" scoring gap, not a regression from randomized spawn itself — randomization just made a valley-trap layout easy to hit instead of relying on the fixed-layout's terrain to happen to line up this way.

**Correction (instrumented repro, 2026-08-10):** the "`flee_dist` is effectively unbounded (~750, half of the 1500 default `awareness_radius`)" assumption above was wrong for this repro — the rabbit's actual runtime `awareness_radius` is far smaller than the 1500 config default (some pack/species overlay scales it down for gameplay at this playfield's ~40-unit scale; source of the override not yet traced). Observed `flee_dist ≈ 7.9` world units throughout.

**Instrumented repro — confirmed mechanism, more fundamental than "bounded pocket outscores real exit":** added temporary logging to `_mint_flee_waypoint` (`motor_planner.gd`, gated by a `_DEBUG_LOG_FLEE_CANDIDATES` const, off by default — flip to `true` to reproduce), pointed `playfield_spawn.locked_layout_path` at `spawn_layout_locked_rt1.json`, and ran `tests/smoke_ai_player.gd` headless. Captured (`user://logs/flee_candidate_debug.log`, 4 re-mints across ticks 585–636 while `ff=1`/`gk=avoid_host` per `motor_explore_tick.log`):

```
t=585 pos=(-70.1,-3.3,-4.5) threat=(-72.4,10.8) flee_dist=7.9 base_dir=(0.14,-0.99) cand[deg:reach]=["0:0.0","60:0.0","120:0.0","180:0.0","240:0.0","300:0.0"] chosen_reach=0.0 give_up=false final_dir=(0.14,-0.99)
t=602 pos=(-70.0,-3.0,-5.4) ... cand[deg:reach]=["0:0.0","60:0.0","120:0.0","180:0.0","240:0.0","300:0.0"] chosen_reach=0.0 give_up=false final_dir=(-0.78,-0.63)
t=619 pos=(-70.7,-2.7,-6.4) ... cand[deg:reach]=[...all 0.0...] final_dir=(-0.91,0.42)
t=636 pos=(-71.9,-3.4,-5.3) ... cand[deg:reach]=[...all 0.0...] final_dir=(0.04,1.00)
```

**All six 60°-apart candidates score `reach=0.0` at every re-mint** — `_flee_candidate_reach`'s `NavigationServer3D.map_get_path` is returning a degenerate (<2-point) path in *every* tested bearing, not just the dead-end ones. Crucially, `give_up=false` on every line too: the 16-direction give-up escalation (triggers whenever `chosen_reach < flee_dist * 0.35`, which `0.0` always satisfies) *also* found nothing better than `0.0` in all 16 finer directions. So this isn't "the dead-end pocket happens to score higher than the real exit" — the scorer has **zero usable signal in any direction** at this position, and bearing selection silently degrades to "first candidate (in fixed 60°-step rotation order) that isn't a recent-backtrack" — i.e., effectively arbitrary. That matches the observed symptom: across the 4 re-mints the chosen heading swings almost 180° tick-to-tick (`final_dir` from `(0.14,-0.99)` to `(-0.78,-0.63)` to `(-0.91,0.42)` to `(0.04,1.00)`) while the rabbit's own world position barely moves in X (stays −70 to −72, i.e. never progresses back toward the real exit) — consistent with "wandering inside the pocket," not a single bad-but-decisive choice.

**Open question — why does `map_get_path` degenerate here:** not yet confirmed. Leading hypothesis: the rabbit's position and/or the candidate endpoints in this valley aren't validly on/connected-to the baked navmesh (same terrain-vs-navmesh-connectivity family as C9/C10 — `NavigationServer3D.map_get_path` returns a trivial 0-1 point path when start/end both snap to the same off-mesh boundary point). Not yet confirmed by direct navmesh-polygon inspection (e.g. `NavigationServer3D.map_get_closest_point_owner` / a raycast-grid probe on the baked navmesh at `(-70, -3, -5)`, same technique used for the original C10 root-cause). A `Body not on floor after spawn` warning appeared later in this same run, but at unrelated positions/ticks — not yet linked to this specific window.

**Root cause confirmed (2026-08-10):** added `NavigationServer3D.map_get_closest_point` / `map_get_closest_point_owner` to the same debug logging and re-ran `tests/smoke_ai_player.gd` twice against the locked layout (the simulation isn't deterministic tick-for-tick even with layout+spawn locked — roaming before the chase catches up varies — so the two runs hit Flight at different positions/ticks, which turned out to be informative):

```
run 1: t=585  pos=(-70.1,-3.3,-4.5) ... nav_closest=(0.0,0.0,0.0) nav_snap_dist=70.32 nav_owner_valid=false
run 2: t=649  pos=(-48.7,-1.6,-5.0) ... nav_closest=(0.0,0.0,0.0) nav_snap_dist=49.02 nav_owner_valid=false
run 2: t=666  pos=(-48.6,-1.3,-5.8) ... nav_closest=(0.0,0.0,0.0) nav_snap_dist=48.92 nav_owner_valid=false
run 2: t=683  pos=(-49.4,-0.9,-6.7) ... nav_closest=(0.0,0.0,0.0) nav_snap_dist=49.82 nav_owner_valid=false
run 2: t=700  pos=(-50.4,-1.7,-5.5) ... nav_closest=(0.0,0.0,0.0) nav_snap_dist=50.68 nav_owner_valid=false
```

`nav_owner_valid=false` is decisive: `NavigationServer3D.map_get_closest_point_owner` returns an invalid RID specifically when **no baked navigation region covers that area at all** — this is not a query-timing artifact (captured live, deep into a stable 3600-tick run, well after bake). It reproduced at **two different positions ~20 world units apart** across the two runs, both while `ff=1`/`gk=avoid_host`, both scoring `reach=0.0` in all 22 tested directions (6 + the 16-direction escalation). So this is a genuine, and apparently not-isolated, navmesh coverage gap in valley/steep terrain — `_bake_playfield_navmesh()` (`main_3d.gd:416-437`) doesn't set `NavigationMesh.agent_max_slope` explicitly (Godot default 45°), so if these valley walls exceed that, or if there's a floor-collision gap in the grasslands mesh itself at these spots, the affected area simply never gets baked into walkable polygons — same "terrain geometry vs. motor assumptions" family as C9/C10, not a flee-scoring-weight issue. Not yet confirmed which of those two (slope-too-steep-for-bake vs. an actual collision gap) is the specific cause, nor whether it's one connected unwalked region or several.

**Compounding gap:** regardless of the navmesh root cause, `_mint_flee_waypoint` has no fallback for "every candidate scored `0.0`, including the 16-direction escalation" — it silently falls through to an arbitrary pick (first non-backtracked candidate in a fixed rotation order) instead of treating a fully-uninformative scan as its own signal.

**Slope theory ruled out (2026-08-10):** extended the same live instrumentation with a 4-point elevation cross-probe (raycast ±3 world units on each XZ axis around the creature) around further repro hits. Observed `dy` (elevation delta over 3 units) topped out around `1.87`, i.e. **~32° at the steepest sampled point — well under Godot's 45° default `agent_max_slope`**. So terrain steepness isn't the limiting factor. Instead, across repeated runs the failing positions trended toward the playfield's actual west edge (X reaching **−92 to −98**, with ground raycasts 3 units further west increasingly returning `hit=false` — no floor collision at all, i.e. off the collision mesh). This is the same scenario `_DEBUG_FORCE_EDGE_CHASE_SPAWN` was built to force (its own comment: *"Rabbit pinned near the left edge... reproduces the boundary ping-pong on demand"*) — not a random interior valley, but the rabbit legitimately being pushed toward/past the map boundary, where navmesh coverage correctly doesn't exist (there's no floor there to bake). **No navmesh-bake fix applies here** — raising `agent_max_slope` wouldn't change anything since slope was never the constraint, and there is no floor-collision gap to fix (the boundary is intentional). Dropped that half of the original two-part plan.

**Fix shipped:** `_mint_flee_waypoint` (`motor_planner.gd`, after the give-up escalation block) — when `final_reach <= 0.0` after *both* scans (the scorer found literally no usable signal in any of the 22 tested directions), stop trusting the arbitrary first-candidate-in-rotation-order pick. Hold the direction toward the previous `flee_waypoint` instead (consistent, not thrashing — same "keep running the way you were already going" principle as the existing C9 7th-fix no-visible-threat latch-hold), falling back to the raw straight-away-from-threat `base_dir` only when there's no prior waypoint yet.

**Verified:** confirmed via the same live instrumentation (temporarily restored, then removed) that `final_dir` now stays stable/converges across consecutive re-mints in the zero-signal case instead of swinging ~180° each time (e.g. `(0.98,0.21)` → `(0.99,0.16)` → `(1.00,0.05)` → `(1.00,-0.03)` → `(1.00,-0.04)` → `(1.00,-0.04)`, vs. the wild pre-fix swings quoted above). Full `tests/run_all.gd` suite green (0 assertion failures) both before and after; 5 additional `tests/smoke_ai_player.gd` headless runs post-fix with no compile/runtime errors. **Not claimed:** this doesn't solve escaping a genuine corner near the map edge when the threat itself is also converging on the held heading — that's the already-documented R1 architecture-risk trade-off (greedy per-tick decisions near boundary geometry), not something this fix set out to or could fully close.

**Diagnostic cleanup:** the temporary `_DEBUG_LOG_FLEE_CANDIDATES`-gated logging (candidate reaches, `nav_closest`/`nav_owner_valid`, elevation cross-probe) used to gather all evidence above was removed from `motor_planner.gd` after use, per the existing "throwaway probe, written and deleted" convention (see C10 history) — this doc retains the full evidence trail instead.

### RT3 — Boulders / shrubs reported spawning outside the playfield

**Status:** `open` — reported by the user during manual playtesting; not yet reproduced in headless testing, so not yet root-caused.

**Report:** "some boulders and shrubs appeared to spawn outside the playfield and I wasn't getting random object placement."

**Investigated so far:**
- **Random object placement:** confirmed working — `game_config.json`'s `playfield_spawn.locked_layout_path` is empty (no leftover lock from RT1/C11 diagnostic sessions), and 4 separate fresh headless `tests/smoke_ai_player.gd` runs produced 4 distinct seeds and distinct interior-boulder/food layouts. Clarified with the user: they were clicking "New Game" within the same running session, not relaunching the app — boulders/food are session-lifetime-fixed by current design (only re-rolled in `_build_playfield()`, called once from `_ready()`; only the duel pair re-rolls per `new_game()`), so "no new layout on New Game click" is working as designed, not this bug. **Separately:** `_DEBUG_FORCE_EDGE_CHASE_SPAWN` has silently pinned the duel pair to a fixed, non-random spawn on every run all session (see [CLEANUP.md C11](CREATURE_MOVEMENT_V3_CLEANUP.md#c11-goal-hub-incumbent-flip-flops-find_foodrestavoid_hostiles-on-single-tick-threat-sampling) open question) — if that's what looked "not random," that's the real cause, tracked there.
- **Out-of-bounds props:** across 4 fresh headless runs, every single `"no ground hit for prop"` warning (172, 171, 171, 171 respectively) traced back to **perimeter boulders only** — a fixed, un-randomized grid pattern along the AABB edges (`PlayfieldPerimeterBoulders.place_along_perimeter`, unrelated to this session's randomizer work) landing on stretches of the playfield's rectangular collision AABB where the actual (evidently non-rectangular) grasslands terrain has no floor. **Zero** warnings traced to randomized interior boulders/food in any of the 4 runs — `pick_uniform_fraction`'s edge margin appears to be keeping randomized objects clear of this specific gap, at least for the seeds tried.

**Open questions:**
- Is the user's report actually about the (pre-existing, unrelated-to-randomization) perimeter-edge gap above, mis-attributed to the new feature since it's the first time spawn positions were watched closely? Or does the randomizer genuinely produce an out-of-bounds placement at some seed not yet hit in 4 headless samples — `edge_margin_m` (default 1.6, `playfield_spawn_randomizer.gd`) is a flat buffer from the *rectangular* AABB edge and has no awareness of the terrain's actual (apparently irregular) shape, so a bad-luck seed landing near a real cutout is plausible even though not yet observed.
- Not yet run: a larger headless batch (10+) specifically watching for `"no ground hit for prop"` warnings at non-grid-pattern (i.e. genuinely random) coordinates, and/or a wider `edge_margin_m` or a ground-verification rejection check in `pick_uniform_fraction` (currently it only respects the rectangular bounds, never verifies real ground exists at the candidate point — unlike `_snap_playfield_props_to_ground`'s after-the-fact raycast, which only warns, never rejects/retries).
