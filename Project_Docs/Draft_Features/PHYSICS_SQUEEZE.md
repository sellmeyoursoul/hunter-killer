# Hunter Killer — Physics/size passability & shelter squeeze model

> **Status:** Draft — design complete as of 2026-09-17. §4a/§4d/§4e/§4f/§4g/§4i/§4j are resolved, §4b/§4c are moot, and §4h (`crush_weight`) is explicitly out-of-scope-and-non-blocking by user decision, not an oversight. **The original implementation-blocking condition on this doc is cleared** — this line stays only until the user explicitly confirms they want implementation to start (see closing note in the 2026-09-17 changelog entry); nothing here should be treated as a green light on its own.

## 1. Why this doc exists

Started as a narrow question — "should flee weight a nearby known-safe spot more than running into the open?" — during live-duel debugging (see [CREATURE_MOVEMENT_V3_CLEANUP.md](CREATURE_MOVEMENT_V3_CLEANUP.md) C21/C22 for the bugs that prompted it). Investigating that surfaced that the game's only current "prey can pass, predator can't" mechanic (`open_shrub_3d`'s `MobBlocker` on physics layer 8, gated purely by `is_hostile`/feeding-mode) is a diet-role hack, not a size mechanic — and that trying to bias flee toward such a spot runs headlong into the shared `NavigationRegion3D`'s bake including all collision layers for every agent regardless of species. Chasing that down reopened the question of what "can this creature pass this obstacle" should actually mean in a game whose stated scale range is mouse to mastodon. That's a foundational, world-model-level decision — hence its own doc, not a paragraph in the flee-weighting design.

**Downstream of this doc:** the original flee-shelter-weighting work (tier gating, bonus vs. override, destination/route threat clearance) is blocked on the decisions here, since it needs a real passability primitive to check "is the path to shelter actually clear" against. See [CREATURE_MOVEMENT_V3_CLEANUP.md](CREATURE_MOVEMENT_V3_CLEANUP.md) for that thread once this doc is resolved.

## 2. Existing systems inventory (as found 2026-09-16/17)

Three separate, only-partly-related systems currently touch "can a creature go here":

### 2a. Physics collision layers (diet-role based, live)
`_apply_physics_layers()` ([creature_kinematic_body_3d.gd:225-231](../../creature/capabilities/creature_kinematic_body_3d.gd#L225-L231)) assigns collision purely off `is_hostile` (derived from `feeding_mode`):

| Layer/mask | Bit(s) | Meaning today |
|---|---|---|
| Layer 1 | terrain / world-static | Universally solid — must stay exempt from any tiering. Matches `line_of_sight.gd`'s `WORLD_STATIC_MASK`. |
| Layer 2 | herbivore body | `collision_layer` for non-hostile creatures. |
| Layer 4 | carnivore body | `collision_layer` for hostile creatures. |
| Layer 8 | `plant_mob_block` | Blocks carnivore movement only (carnivore mask = 9 = 1+8; herbivore mask = 1, excludes it). Source of the shrub-refuge "predator can't follow, prey can" trick. |

Concrete current assets on this scheme:
- `open_shrub_3d.tscn`: `MobBlocker` at layer 8 / mask 4 — the diet-role permeability trick.
- `solid_shrub_3d.tscn`: its own `StaticBody3D` at layer 1 / mask 7 (1+2+4) — already blocks *everyone* uniformly; arguably already correct under a size/physics model and may not need to change.
- `playfield_bounds_3d.gd`, `main_3d.gd`'s floor body: layer 1, universally solid (correct, out of scope for tiering).
- `MobHitbox` (Area3D, predation-catch detection) is a **separate system** from body collision layers — not in scope for this doc; see §4 open question on combat/MobHitbox review.

Nothing flagged that drift when it happened. Full reconciliation below, sorted into three buckets per 2026-09-17 review instruction: **(1) wired but unused/unverified — review closely, don't assume it works as documented; (2) wired but superseded — flag for removal; (3) never wired — review for alignment with current design or as a still-good idea.**

## 3. Decisions locked in so far

These are settled for this design (revisit only if something below invalidates them):

1. **Remove the diet-role-based physics layer split** (layers 2/4/8 keyed off `is_hostile`) for *movement passability* specifically. Passability should be driven by physics/size, not predator/prey identity.
2. **`is_hostile` is not being removed** — it stays load-bearing for `DietRegistry`, predation eligibility, threat/awareness classification. Only its role in *physics passability* is being cut.
3. **Real collision resolution (`move_and_slide`) cannot do live radius-vs-radius comparison** — it's a static per-body layer/mask system. Whatever replaces the diet-role layers for *actual movement blocking* needs to be either discrete size-tier layers, or routed through the §2b grid/cell system's `can_enter`/`movement_speed_multiplier` queries (exact mechanism is the central open question, §4a). A live, continuous shape-cast (arbitrary radius, decoupled from any object's own `collision_layer`) is available and appropriate for **AI decision-making** (planner-side "can I fit / can they not" checks) on top of whatever real-time collision uses — these are two different layers of the system, not one.
4. **Obstacle passability authoring**: current thinking (reassess-able) is a per-object *trait* for authored content like plants (i.e., `fit_size`, matching §2b/§2c already), vs. geometry-derived measurement for things like boulders where hand-authoring doesn't make sense.
5. **Runtime size changes should be able to move a creature between tiers** — agreed as a requirement for future growth/magic systems, even though nothing consumes it yet.
6. **All existing passability-relevant content must be migrated to the new scheme** — doing this now, while the surface area is small, specifically to avoid a second migration later. Concrete inventory in §2a/§6.
7. **Threat-size estimation for AI decisions runs through `stat_composure`, not `stat_observation`** — "Keep clear judgment under stress" ([CREATURE_ATTRIBUTES_USAGE.md §3.4](../Definitive_Features/CREATURE_ATTRIBUTES_USAGE.md)) is the right semantic match for "an easily frightened creature is less likely to make an accurate estimate of a threat's size than one with calm nerves." Already **live (partial)** for the `WAIT` concealment-rest calorie discount via `CreatureStatCurve.saturating` — same curve tooling likely reusable.
8. **Belief confirmation should stay ground-truth; noise applies only at real-time tactical decisions** (proposed, not yet explicitly re-confirmed by the user this session — treat as tentative default, not locked, until restated). Mirrors the existing convention: food-yield noise never touches the real `max_calories` grant, only the momentary live-vs-locale handoff choice.
9. **Shelter belief tiers, from the C22 follow-on discussion:**
   - An `observed` shelter belief + a witnessed threat-free *quiet streak* while there (no real threat ever came close — passive, structural evidence only) promotes to **`confirmed`** (not `battle_tested`).
   - **`battle_tested`** is reserved for "an actual threat couldn't get me because I was in the shelter" — real evidence of a genuine chase-then-escape, not just a quiet period. **Resolved (§4e, 2026-09-17):** the trigger for this is `flight_just_entered`/`flight_just_exited` (already computed in `creature_motor_stack.gd` for fast-flight-path tracking) — a real acute-threat flight episode that *ends* while the creature is at/near a shelter is direct evidence that shelter is what let it escape. This **replaces** the existing `notify_safety_recovered_near_shelter` trigger (which just fired on the generic `safety_met` counter going true nearby — no requirement a real threat was ever actually closing). Because this is strictly stronger evidence than the geometric STAY-evaluate confirm ever provides, it promotes **directly to `battle_tested` from either `observed` or `confirmed`** — it doesn't need to pass through `confirmed` first.
   - Both `observed` and `confirmed`/`battle_tested` tiers should contribute to flee's shelter bias (`consult_shelter_beliefs` currently hard-excludes `observed` entirely) — confirmed should just carry more weight than observed.
10. **Flee's shelter bias stays entirely inside `GOAL_AVOID_HOSTILES`'s own bearing selection** — not promoted to making `GOAL_SHELTER` itself outweigh `GOAL_AVOID_HOSTILES` at top-level goal arbitration.
11. **The shelter flee-candidate should score on pure reach**, not get automatically excluded by whatever "is this a dead end" logic exists elsewhere — being a geometric dead end is exactly what makes it valuable here (believed inaccessible to the hostile), not a liability. (Investigation this session found dead-end *memory* specifically doesn't intersect flee's candidate scoring at all today, so this is more a "don't accidentally introduce this exclusion" guardrail than a fix to an existing one — see §4f.)
12. **Enclosure/pocket shelter and squeeze-gap/choke-point passages are likely separate mechanics**, not one — different belief shape (point vs. route/segment), different behavioral use (destination vs. through-passage). Worth designing separately rather than cramming both into the existing `GOAL_SHELTER`/`shelter_map_confidence` system. Not yet designed either way.
13. **Existing enclosure-shelter has a real, independent correctness gap**: `_ShelterProbe.enclosure_fraction`/STAY-evaluate confirm never checks whether the *specific pursuing threat* can also fit through the enclosure's opening. A "confirmed" shelter today could, in principle, be a trap a same-size-or-smaller predator can follow the prey straight into. Needs its own fix once the passability primitive (§4a) exists.
14. **Wolf reskin — scale up as a real size-differentiated archetype.** Fox has already been reskinned to a wolf visually; scale both the model and the creature profile (`creature_size`, `collision_capsule_radius`, associated mesh/collision) up roughly **3x** relative to fox, to create a genuine size gap for testing/tuning the squeeze mechanic against. This is actionable independent of the tier scheme being finalized (it's tuning one archetype's raw numbers), though final capsule-radius targets may need revisiting once tier boundaries are set.
15. **MobHitbox flagged for review once combat lands** — the predator/prey dichotomy it currently assumes will dissolve once any creature can interact directly with any other (combat, and per user: likely also mating and non-violent resource-sharing). Not in scope now; tracked so it isn't forgotten when combat design starts.
16. **§4a resolved (2026-09-17): query-enforced, not physics-engine-enforced, for everything except layer-1 terrain.** Terrain keeps real physics-layer solidity, unchanged, engine-enforced. For everything else, the motor's own locomotion code decides passability by querying a data model *before* committing a movement step, rather than relying on `move_and_slide`'s automatic collision response — because physics layers are binary per body and can't express continuous, size-relative impact, which is what's wanted for essentially everything that isn't immobile terrain. Two mechanisms, split by geometry shape, both query-enforced:
    - **Object-scale (individual shrubs, boulders, enclosure mouths — anything with a discrete, meaningfully-shaped boundary):** a shared, movement-inert "query-only" physics layer (reusing one of the bits freed by retiring the diet-role split, §3.1) that these objects get a *real* `CollisionShape3D` on, sized/derived from the object's actual model geometry (reusing the mesh-AABB-to-collision-shape derivation `creature_kinematic_body_3d.gd`'s `apply_capsule_footprint_from_visual()` and `bush_food_3d.gd`'s `_sync_mesh_collision_from_visual`/`_StaticObstacleCollision` already do for creatures and bushes respectively — not new machinery). This layer is excluded from every creature's *real* movement `collision_mask`, so it never physically blocks anyone. The motor shape-casts the moving creature's own actual capsule radius against it before allowing a step. This gives exact, continuous, per-instance/per-creature comparison (a real 0.6m rabbit vs. a real 0.7m fox, not "small" vs. "medium" buckets) — **retires the need for discrete size tiers for this purpose**, superseding §4b/§4c as originally framed (see their updated status below).
    - **Field-scale (continuous area effects with no discrete shape to squeeze through — mud, snow, water):** the existing `EnvironmentCellData`/`EnvironmentGridBaked` grid (§2b), unchanged in concept from what's already implemented, just finally wired to something.
    - **Creature-vs-creature** doesn't need the query-only layer at all — each creature already has a real, correctly-sized, always-current body collider (already excluded from every other creature's real movement mask today, confirmed: neither herbivore mask=1 nor carnivore mask=9 includes the other's body layer). A future "can I push past this other creature" check would shape-cast directly against that creature's existing body shape, no separate representation needed.
    - **Overlap/composition rule** (e.g. a shrub rooted in a water cell): reuses `EnvironmentMovementImpact.merge_greatest_impact()`'s existing precedence exactly, just broadened to accept inputs from both mechanisms, not only grid cells. Order: (1) **hard gate first** — any single source saying "you cannot be here" (object shape-cast blocks, or a field cell's own Mode-A) wins outright, regardless of what anything else says; (2) **if the move is allowed, take the single worst continuous `movement_impact` among every source that applies** (object Mode-B slowdown, field cell slowdown, etc.) — **not stacked/multiplicative**. **First-pass decision (2026-09-17):** worst-alone, no compounding, even when an object-scale and a field-scale slowdown coincide at the same point — revisit later if playtesting says standing in *both* effects at once should feel worse than either alone.
    - **Performance note, not a decision:** object-scale shape-casts only need to check nearby colliders (standard broad-phase spatial query), same pattern already used by `_ShelterProbe`/blocked-approach checks — not a full-scene scan per movement step.
17. **§4d resolved (2026-09-17): automatic geometry-derived sizing by default, for now.** Every object gets its query-only collider sized from its actual model geometry (§3 decision 16); no authored-override mechanism is being built yet. If a specific case needs its gap to differ from its visual silhouette later, add that override then — not speculatively now.
18. **§4i resolved (2026-09-17): decision 8 confirmed, and the noisy quantity is a raw size/radius estimate.** Ground truth stays stored; noise applies only at the moment of a real-time tactical decision (decision 8 is no longer tentative). What's actually being estimated at that moment, now that §4a killed tiers and §4g gave a concrete worked example: a raw size/radius value — a stored belief (self's own radius, or a remembered passer's known size from a squeeze/shelter belief) compared against a live, `stat_composure`-noised estimate of a specific threat's size. Not a tier index (tiers don't exist post-§4a/§4b) and not a grid `fit_size` result (that only governs the unrelated field-scale speed-multiplier case, not a "does this specific threat fit" question).
19. **§4g resolved (2026-09-17): choke-point/squeeze-gap belief model.** A separate belief type from shelter (decision 12), same underlying row-storage machinery (`goal_belief_memory.gd`'s loc-keyed, tiered pattern) but its own bucket and its own tier semantics:
    - **Two-tier evidence model, not three** — `observed` and `confirmed` only. No `battle_tested`: shelter's third tier exists to capture *protective efficacy* (something direct experience alone can't prove), but a squeeze gap's width is a physical fact — walking through it already gives ground truth, no adversarial validation adds anything further.
    - **`observed`**: a distance/angle-estimated guess at the gap's size, noisy, weight scales down with distance/angle at observation time (reuses the composure/observation stat-curve tooling already built for decision 7, just a separate curve instance keyed to `stat_observation` instead of `stat_composure`).
    - **`confirmed`**: set when a creature actually passes through. Stores that **passer's own known size** as the confirmed value — not a geometric measurement of the true opening width. This is a deliberate simplification, not an approximation error: it's exactly the fact needed for the (currently unwired) inverse/interception case — a pursuer who has observed or confirmed a gap can compare a fleeing creature's known/estimated size against the stored passer-size to judge "that thing fits through something I can't confirm as safe for me," and choose to break off and flank the far side rather than follow. Not wired anywhere yet; flagged as a real future consumer of this same belief, not a hypothetical.
    - **Ground-truth-vs-noise (this is this belief type's answer to §4i):** `confirmed` is stored as-is, ground truth, no noise applied at storage time. Noise only re-enters at tactical use, when a creature compares a stored gap value (its own or a remembered passer's) against its live, composure-noised estimate of a *specific* threat's size — consistent with decision 8's existing default, now concretely instantiated for a second belief type.
    - **Not a goal of its own.** Consulted as a weighted input inside other goals' existing decision points — flee/`GOAL_AVOID_HOSTILES` bearing selection is the obvious consumer (same integration pattern as shelter, decision 10), but explore may also want to weight passing near an `observed`-only squeeze point higher than equivalent open ground, purely to convert it to `confirmed`.
    - **Weighting during flee is a factor, not a binary gate** — combines evidence tier (confirmed outweighs observed) with distance to the point at decision time (a nearby squeeze/shelter should generally outweigh a farther one, and a farther `confirmed` gap can still outweigh a nearer `observed` one, exactly the tradeoff you described). Exact weighting formula is implementation-time detail, not resolved here, but should probably share its shape with shelter's analogous weighting (`shelter_tier_weight` plus a distance term) rather than being invented independently.
    - **Decay reuses the existing generic belief-memory tiering** already implemented in `goal_belief_memory.gd` (precise → coarse/relative → forgotten, `maintain()`), the same mechanism every goal kind already rides on (not something special-cased for food) — just with its own goal-kind-scoped TTL/radius overrides, mirroring the existing `_shelter`-suffixed override pattern (e.g. `goal_memory_ttl_sec_shelter`). `confirmed` rows likely want generous overrides given the value is a durable physical-ish fact; `observed` rows can use tighter/default decay.
    - **Separate storage bucket** — own `goal_kind` (e.g. `GK_CHOKE_POINT`), own table, not shelter's rows. Shelter and squeeze are different mechanics that happen to share row-shape machinery, not one system.
    - **Multi-mouth/tunnel topology is explicitly out of scope for now.** A gap is stored as a single mouth point + radius; a passage with multiple mouths gets each mouth stored independently, with **no recorded relationship between them**. Modeling a real underground-passage/multi-entrance topology is its own design session or later — not needed for the current single-mouth-squeeze and enclosure-with-one-opening cases this doc is actually solving.
    - **Shares its primitive with decision 13's known enclosure-mouth gap** — "can this specific pursuer fit through the shelter's opening" is the same measured/known-size-vs-threat-size comparison, just applied at a shelter's mouth instead of an open-terrain choke point. The mouth is a squeeze belief; what's inside is the shelter belief (decision 12) — same physical object, two different anchor points, two different belief types, already-designed comparison logic reused for both.
20. **§4j resolved (2026-09-17): flee-bias strength and route-clearance mechanics.**
    - **Bonus, not override.** A shelter/squeeze belief adds to a candidate bearing's existing score; it never unconditionally wins over open ground or overrides the base avoid-hostiles scoring.
    - **Race-margin function for route-clearance**, replacing the abandoned navmesh-path-reuse plan: compare the creature's distance to the candidate point against the (nearest relevant) threat's distance to that *same* point — a "who gets there first" proxy. Explicitly **not speed-aware for now** — equal-speed assumption, since real speed/cornering precision is a deliberately deferred future refinement (see below), and a rough proxy is acceptable ("doesn't have to be perfect"). The resulting margin drives the bonus/penalty, monotonically: a clearly-favorable margin → large bonus; a close/uncertain race → smaller bonus (attempting a toss-up isn't punished); a margin suggesting the creature loses the race → bonus drops to zero; a margin that's clearly losing → **negative weight** (actively discourages committing to a path that's already lost, since that both wastes flight distance and can cut off better options). Exact function shape/thresholds (piecewise vs. continuous, where the zero-crossing and "clearly losing" cutoff sit) is implementation-time tuning, not decided here.
    - **Composure-driven size-estimate noise (§3 decision 7) scopes to the fit judgment only** — it decides whether "I fit and the threat doesn't" is judged true/false/uncertain for a given squeeze belief. It does **not** additionally scale the resulting bonus once that judgment is made — no double-application of noise on top of the race-margin math above.
    - **Candidate pool widens, from nearest-shelter-only to a shared radius envelope.** Today's flee scoring evaluates 8 fixed open-field bearings plus one nearest shelter candidate; that changes to: the 8 open-field bearings, plus **every** shelter/squeeze belief within the same radius used for those 8 bearings — all scored through one common function (base avoid-hostiles term + race-margin bonus, + the fit-gate for squeeze/shelter candidates specifically) and compared directly. This is what enables real multi-target blending — e.g. a squeeze that clears one of two pursuing threats but not the other scores according to the *worst* (most dangerous) margin among threats considered, and can end up scoring below clear open ground with no threats nearby, exactly as intended.
    - **Threat aggregation when multiple threats are present**: worst-case margin across all threats currently being considered for avoidance (not summed/averaged) — being caught by any one pursuer is the failure condition, so the most dangerous threat's margin governs. Exact set of "threats currently being considered" reuses whatever the existing avoid-hostiles threat list already tracks each tick, not new bookkeeping.
    - **The same race-margin function generalizes to the 8 open-field bearings too**, not just shelter/squeeze candidates — unifying scoring across the whole candidate pool instead of having shelter/squeeze use one method and open ground another. In the simple single-threat/open-ground case this degenerates to (doesn't conflict with) today's basic "away from threat" distance heuristic — the race triangle collapses toward a line when there's no third point (the squeeze) to reason about.
    - **Explicitly deferred, tracked as future refinement, not in scope now:** incorporating actual creature speed and cornering/turn-rate into the race-margin math for better precision on off-angle approaches. Current math is pure-distance, equal-speed proxy; revisit once/if the coarse version proves insufficient in practice.
21. **§4f resolved (2026-09-17): dead-end handling — shared check subroutine + belief-overlap override.**
    - **One shared subroutine, not a mint-pipeline refactor.** No single common low-level "mint a waypoint" call exists today — `_mint_locale_search_waypoint`, `_mint_explore_objective_for_goal`, `_mint_flee_waypoint`, the C1 pursuit-detour latch, and shelter's own precise-candidate approach are five independent functions. Rather than restructure them into one pipeline, add one shared check function, called identically from each site's own tail — same shape as the `is_waypoint_dead_end` call `motor_explore_seek.gd` already makes today, just with the override folded in. Centralizes the *logic*, not the call graph.
    - **Stays a plain boolean, no new stored attribute.** The subroutine returns a single disqualify/allow result; no `dead_end` field gets added to candidate/waypoint dicts or threaded through state. Keeps the footprint minimal — each mint site just skips/rejects a disqualified candidate and tries another, exactly like explore does today.
    - **Two-step logic:** (1) cheap early-out — run the existing `is_waypoint_dead_end` query (already goal-kind-scoped, bounded to ≤12 marks/creature, 15s TTL); if it's not a known dead end, allow immediately, no further work — this is the common case. (2) Only if it *is* a known dead end, scan known beliefs (any goal kind, any tier — food, shelter, squeeze, anything) for one whose location overlaps the same spot (reuse `dead_end_match_radius` for this overlap radius too, for consistency). Any overlap at all is sufficient to override — **no confidence-tier threshold needed**, which simplifies away the earlier open sub-question about how confident a belief has to be.
    - **Overlap found → allow.** No overlap → disqualify, candidate gets skipped. This generalizes decision 11's flee-to-shelter case for free — a shelter belief's own location typically *is* the dead-end pocket being evaluated, so it already satisfies the override without any goal-specific carve-out.
    - **Performance is a non-issue by construction** — both scans involved are already small, bounded, per-creature lists (≤12 dead-end marks, ~25 belief rows per the existing `goal_memory_max_entries` default), not a scene-wide or spatially-indexed structure. Worst case is on the order of a few hundred comparisons, only on the already-rare "this is a known dead end" branch.
    - **Remaining implementation-time detail, not blocking:** the concrete rollout list of five mint sites above still needs each to actually call the new shared check at its tail — an audit/wiring task, not a further design question.

## 8. Risks, gaps, and trade-offs not yet explicitly decided (review, 2026-09-17)

With §4 fully resolved, a review pass against the actual code (not just the doc) surfaced several things that are either genuine unaddressed gaps or trade-offs the decisions above made implicitly without stating them. None of these invalidate anything in §3 — they're mostly "the next layer of decisions below the ones already made," but a few are large enough to want an explicit answer before or during implementation rather than being discovered mid-build.

### 8a. Largest gap: NavigationServer3D's single shared navmesh was never reconciled with per-instance passability
This is the same problem §1 opened with — "trying to bias flee toward such a spot runs headlong into the shared `NavigationRegion3D`'s bake including all collision layers for every agent regardless of species" — and decision 16 resolves real-time movement collision, but **never revisits navmesh baking**. Confirmed in code: `main_3d.gd`'s `_bake_playfield_navmesh()` never sets `geometry_collision_mask`, so it defaults to "all layers" (Godot's own default). That has a real, unresolved consequence either way:
- If the new query-only layer's collider shapes get included in the bake (the default, if nothing changes), `NavigationServer3D` will bake a permanent hole around every squeeze object for *every* creature — nobody will ever get routed through a gap, rabbit or fox, because pathfinding treats it as solid terrain. This would silently defeat the entire mechanic at the pathfinding layer even if the live shape-cast logic is implemented perfectly.
- The fix is presumably to exclude the query-only layer from the bake mask, so the navmesh treats every squeeze gap as open floor — but that has its own consequence nothing here has designed for: a fox's *path* will now happily route it straight at a gap only a rabbit fits through, and its live shape-cast will reject the step it's already committed to via pathfinding. The motor needs a real "blocked mid-path, replan" story for this — `apply_blocked_objective_resolution` already exists and is goal-generic, which is promising (it may already be the right tool), but this doc never states "yes, size-mismatched creatures will path into gaps and bounce off, and that's expected/handled by X" as a decision.

This needs an explicit call — not a large design conversation, but a concrete one: what does `geometry_collision_mask` bake to, and what's the accepted behavior when a creature's own path leads it into a gap it doesn't fit through?

### 8b. Line-of-sight/occlusion never got reconciled with the layer changes
Already self-flagged once in §2b bucket 3 ("worth checking for overlap with the awareness system... not checked this session") but worth resurfacing now that implementation is imminent. Confirmed in code: `line_of_sight.gd`'s occlusion query uses `WORLD_STATIC_MASK := 1` only ([line_of_sight.gd:6](creature/motor/line_of_sight.gd#L6)) — layer 1, nothing else. Today's shrubs (layer 8, or solid_shrub's own layer-1 body) already interact with this inconsistently; under the new model, object-scale obstacles move to a dedicated query-only layer that LOS doesn't check at all. Net effect: a boulder or dense shrub a creature can't physically fit through still won't block *sight* — a threat can be "seen" straight through something it can't walk through. That might be fine (maybe intentional — thin shrubs are visually porous) or might not (a solid boulder should probably occlude). Not decided either way.

### 8c. A concrete, already-existing consumer of the old layer trick will silently break: the debug refuge-cluster feature
`main_3d.gd`'s `_DEBUG_FORCE_OPEN_SHRUB_REFUGE_CLUSTER` (currently `true`, [main_3d.gd:41](main_3d.gd#L41)) exists specifically to test the old diet-role permeability trick on `open_shrub_3d`'s `MobBlocker` (layer 8). It isn't listed in §6's migration table. It needs to be explicitly re-verified (or retired/rewritten) once `open_shrub_3d.tscn` moves off layer 8, or it'll silently stop doing anything meaningful without an obvious failure signal.

### 8d. Trade-off not discussed: continuous per-instance sizing creates a flicker/hysteresis risk that discrete tiers didn't have
Decision 16's continuous shape-cast comparison is a real improvement over tiers, but it comes with a cost the doc frames as pure upside: because size is runtime-mutable (decision 5) and every fit judgment is presumably re-evaluated live, a creature near a threshold size (a buff/debuff ticking on/off, or a noisy composure-driven threat-size estimate wobbling near the boundary) could flip between "I fit" and "I don't fit" moment-to-moment. Discrete tiers had this problem too in principle, but continuous values plus live noise make it more likely to land exactly on a knife's edge. Worth a debounce/hysteresis note for implementation (e.g., don't re-roll the fit judgment every tick once a squeeze approach has committed) rather than discovering it as visible twitchy behavior later.

### 8e. Unaddressed: what happens on interpenetration/edge-case overlap with a purely query-enforced model
Real physics collision self-corrects overlap (bodies get pushed apart automatically). A query-only, check-before-you-move model has no equivalent — if a creature ever ends up overlapping a collider it shouldn't fit through (spawn placement, a shrink-then-regrow size buff, another creature shoving it), every proposed step could fail the query with no built-in escape path, a potential soft-lock. Not designed anywhere yet; likely needs an explicit "always allow a step that strictly increases clearance/distance from the blocking shape, even if the destination itself would also fail" escape hatch.

### 8f. Unaddressed: `confirmed` squeeze-belief update policy when multiple different-sized creatures pass the same gap over time
Decision 19 stores the *passer's own known size* at confirm time — correct as far as it goes, but doesn't say what happens on a **second** confirmation of the same belief row by a differently-sized creature. Ratchet to the largest known passer (monotonic, most useful for later "can anything my size get through" reasoning, but means a stale first-confirmer's tiny size could artificially cap the belief if a bigger creature later confirms and it isn't ratcheted), or just overwrite with the most recent passer (simpler, but can *regress* a previously-learned larger fact when a smaller creature passes later)? This has real behavioral consequences and isn't just a tuning knob — worth a real answer, not an implementation-time footnote.

### 8g. Trade-off not discussed: no shared/herd belief propagation
Every belief (shelter, squeeze) lives in a creature's own individual `memory_adapter` — nothing here proposes or rules out sharing discoveries between creatures (e.g., a pack, or same-species individuals). That's consistent with the existing architecture and probably the right default, but it's worth naming as a deliberate trade-off rather than an oversight: many individually-dumb creatures will independently rediscover the same squeeze points and shelters over their lifetimes rather than a population "learning" collectively. Fine for now; flagging so it isn't mistaken later for a bug when two same-species creatures behave inconsistently around the same real-world gap.

### 8h. Rollout risk: this touches core per-tick locomotion for every creature, with no staging/rollback story
Decision 16 replaces engine-enforced collision with motor-owned query logic for nearly everything except terrain — a foundational change to code that runs every physics tick for every creature. The doc doesn't discuss a staged rollout (e.g., feature-flagged, ship query-only layer + shape-cast for one obstacle type first and validate before converting all diet-role assets at once) versus a single cross-cutting migration. Given the project's own regression-test discipline (every bug gets a test, per the C-numbered cleanup doc convention) and how much surface this touches, worth deciding explicitly whether to convert everything in one pass or stage it — not because either is wrong, but because nothing above says which.

None of 8a-8h block starting the work — 8a and 8c are the two I'd actually want answered *before* writing code, since 8a can silently defeat the whole feature and 8c is a known regression waiting to happen. The rest are fine to resolve as they're hit during implementation, as long as they're not forgotten.
