## 1. Why this doc exists

Started as a narrow question — "should flee weight a nearby known-safe spot more than running into the open?" — during live-duel debugging (see [CREATURE_MOVEMENT_V3_CLEANUP.md](CREATURE_MOVEMENT_V3_CLEANUP.md) C21/C22 for the bugs that prompted it). Investigating that surfaced that the game's only current "prey can pass, predator can't" mechanic (`open_shrub_3d`'s `MobBlocker` on physics layer 8, gated purely by `is_hostile`/feeding-mode) is a diet-role hack, not a size mechanic — and that trying to bias flee toward such a spot runs headlong into the shared `NavigationRegion3D`'s bake including all collision layers for every agent regardless of species. Chasing that down reopened the question of what "can this creature pass this obstacle" should actually mean in a game whose stated scale range is mouse to mastodon. That's a foundational, world-model-level decision — hence its own doc, not a paragraph in the flee-weighting design.

**Downstream of this doc:** the original flee-shelter-weighting work (tier gating, bonus vs. override, destination/route threat clearance) is blocked on the decisions here, since it needs a real passability primitive to check "is the path to shelter actually clear" against. See [CREATURE_MOVEMENT_V3_CLEANUP.md](CREATURE_MOVEMENT_V3_CLEANUP.md) for that thread once this doc is resolved.

## 2. Existing systems inventory (as found 2026-09-16/17)

Three separate, only-partly-related systems currently touch "can a creature go here":

### 2a. Physics collision layers (diet-role based, live)
`_apply_physics_layers()` ([creature_kinematic_body_3d.gd:225-231](../../creature/capabilities/creature_kinematic_body_3d.gd#L225-L231)) assigns collision purely off `is_hostile` (derived from `feeding_mode`):

| Layer/mask | Bit(s) | Meaning today |
|---|---|---|
| Layer 1 | terrain / world-static | Universally solid — must stay exempt from any tiering. Matches `line_of_sight.gd`'s `WORLD_STATIC_MASK`. |
| Layer 2 | herbivore body | `collision_layer` for non-hostile creatures. |
| Layer 4 | carnivore body | `collision_layer` for hostile creatures. |
| Layer 8 | `plant_mob_block` | Blocks carnivore movement only (carnivore mask = 9 = 1+8; herbivore mask = 1, excludes it). Source of the shrub-refuge "predator can't follow, prey can" trick. |

Concrete current assets on this scheme:
- `open_shrub_3d.tscn`: `MobBlocker` at layer 8 / mask 4 — the diet-role permeability trick.
- `solid_shrub_3d.tscn`: its own `StaticBody3D` at layer 1 / mask 7 (1+2+4) — already blocks *everyone* uniformly; arguably already correct under a size/physics model and may not need to change.
- `playfield_bounds_3d.gd`, `main_3d.gd`'s floor body: layer 1, universally solid (correct, out of scope for tiering).
- `MobHitbox` (Area3D, predation-catch detection) is a **separate system** from body collision layers — not in scope for this doc; see §4 open question on combat/MobHitbox review.

Nothing flagged that drift when it happened. Full reconciliation below, sorted into three buckets per 2026-09-17 review instruction: **(1) wired but unused/unverified — review closely, don't assume it works as documented; (2) wired but superseded — flag for removal; (3) never wired — review for alignment with current design or as a still-good idea.**

## 3. Decisions locked in so far

These are settled for this design (revisit only if something below invalidates them):

1. **Remove the diet-role-based physics layer split** (layers 2/4/8 keyed off `is_hostile`) for *movement passability* specifically. Passability should be driven by physics/size, not predator/prey identity.
2. **`is_hostile` is not being removed** — it stays load-bearing for `DietRegistry`, predation eligibility, threat/awareness classification. Only its role in *physics passability* is being cut.
3. **Real collision resolution (`move_and_slide`) cannot do live radius-vs-radius comparison** — it's a static per-body layer/mask system. Whatever replaces the diet-role layers for *actual movement blocking* needs to be either discrete size-tier layers, or routed through the §2b grid/cell system's `can_enter`/`movement_speed_multiplier` queries (exact mechanism is the central open question, §4a). A live, continuous shape-cast (arbitrary radius, decoupled from any object's own `collision_layer`) is available and appropriate for **AI decision-making** (planner-side "can I fit / can they not" checks) on top of whatever real-time collision uses — these are two different layers of the system, not one.
4. **Obstacle passability authoring**: current thinking (reassess-able) is a per-object *trait* for authored content like plants (i.e., `fit_size`, matching §2b/§2c already), vs. geometry-derived measurement for things like boulders where hand-authoring doesn't make sense.
5. **Runtime size changes should be able to move a creature between tiers** — agreed as a requirement for future growth/magic systems, even though nothing consumes it yet.
6. **All existing passability-relevant content must be migrated to the new scheme** — doing this now, while the surface area is small, specifically to avoid a second migration later. Concrete inventory in §2a/§6.
7. **Threat-size estimation for AI decisions runs through `stat_composure`, not `stat_observation`** — "Keep clear judgment under stress" ([CREATURE_ATTRIBUTES_USAGE.md §3.4](../Definitive_Features/CREATURE_ATTRIBUTES_USAGE.md)) is the right semantic match for "an easily frightened creature is less likely to make an accurate estimate of a threat's size than one with calm nerves." Already **live (partial)** for the `WAIT` concealment-rest calorie discount via `CreatureStatCurve.saturating` — same curve tooling likely reusable.
8. **Belief confirmation should stay ground-truth; noise applies only at real-time tactical decisions** (proposed, not yet explicitly re-confirmed by the user this session — treat as tentative default, not locked, until restated). Mirrors the existing convention: food-yield noise never touches the real `max_calories` grant, only the momentary live-vs-locale handoff choice.
9. **Shelter belief tiers, from the C22 follow-on discussion:**
   - An `observed` shelter belief + a witnessed threat-free *quiet streak* while there (no real threat ever came close — passive, structural evidence only) promotes to **`confirmed`** (not `battle_tested`).
   - **`battle_tested`** is reserved for "an actual threat couldn't get me because I was in the shelter" — real evidence of a genuine chase-then-escape, not just a quiet period. **Resolved (§4e, 2026-09-17):** the trigger for this is `flight_just_entered`/`flight_just_exited` (already computed in `creature_motor_stack.gd` for fast-flight-path tracking) — a real acute-threat flight episode that *ends* while the creature is at/near a shelter is direct evidence that shelter is what let it escape. This **replaces** the existing `notify_safety_recovered_near_shelter` trigger (which just fired on the generic `safety_met` counter going true nearby — no requirement a real threat was ever actually closing). Because this is strictly stronger evidence than the geometric STAY-evaluate confirm ever provides, it promotes **directly to `battle_tested` from either `observed` or `confirmed`** — it doesn't need to pass through `confirmed` first.
   - Both `observed` and `confirmed`/`battle_tested` tiers should contribute to flee's shelter bias (`consult_shelter_beliefs` currently hard-excludes `observed` entirely) — confirmed should just carry more weight than observed.
10. **Flee's shelter bias stays entirely inside `GOAL_AVOID_HOSTILES`'s own bearing selection** — not promoted to making `GOAL_SHELTER` itself outweigh `GOAL_AVOID_HOSTILES` at top-level goal arbitration.
11. **The shelter flee-candidate should score on pure reach**, not get automatically excluded by whatever "is this a dead end" logic exists elsewhere — being a geometric dead end is exactly what makes it valuable here (believed inaccessible to the hostile), not a liability. (Investigation this session found dead-end *memory* specifically doesn't intersect flee's candidate scoring at all today, so this is more a "don't accidentally introduce this exclusion" guardrail than a fix to an existing one — see §4f.)
12. **Enclosure/pocket shelter and squeeze-gap/choke-point passages are likely separate mechanics**, not one — different belief shape (point vs. route/segment), different behavioral use (destination vs. through-passage). Worth designing separately rather than cramming both into the existing `GOAL_SHELTER`/`shelter_map_confidence` system. **Which bucket a given shelter falls into, clarified (2026-09-18, see decision 13's addendum):** a boundary with one distinguished narrow opening (a den with a real doorway) is the squeeze/mouth case (decision 19); a boundary that's uniformly porous to the occupant and uniformly solid-for-the-threat all the way around (this doc's own canonical shrub-ring example, §1) has no distinguished opening at all and stays entirely in the plain enclosure/pocket case, detected via `_ShelterProbe.enclosure_fraction()` run at a threat radius — no squeeze belief involved.
13. **Existing enclosure-shelter has a real, independent correctness gap**: `_ShelterProbe.enclosure_fraction`/STAY-evaluate confirm never checks whether the *specific pursuing threat* can also fit through the enclosure's opening. A "confirmed" shelter today could, in principle, be a trap a same-size-or-smaller predator can follow the prey straight into. Needs its own fix once the passability primitive (§4a) exists.

    **Concrete fix identified (2026-09-18), corrected same-day.** First pass over-applied decision 19's "mouth" framing here — that's wrong for this doc's own canonical worked example (§1: a ring of shrubs a rabbit passes through everywhere but a wolf can't). A "mouth" only exists when a boundary is otherwise solid with one distinguished narrow opening — that's a different shape from a boundary that's **uniformly porous to the small creature all the way around and uniformly solid-for-the-threat all the way around**, which is what this ring actually is. There is no distinguished opening for a mouth belief to anchor to, so **no squeeze-gap belief gets minted here at all** — this case stays entirely inside the plain enclosure/pocket shelter mechanic (decision 12's other bucket), not decision 19's choke-point bucket. (Decision 19's mouth model is still correct for its own case — e.g. a den with one real doorway a fox might partly enter before failing to fit — just not this one.)

    **The deeper point the correction exposes: the rabbit itself never perceives these shrubs as solid at all.** Its own live per-step shape-cast (decision 16) and the §8a route scan only register a blocker when *its own* radius fails to clear a gap — and it never does, anywhere on this ring. Walking through is indistinguishable, from the rabbit's lived movement experience, from crossing open ground. **Shelter candidacy for this shape can't be derived from the occupant's own passability experience, because that experience is a non-event.** It has to come from a proactive, decoupled geometric probe evaluated at a *hypothetical larger* radius — which is exactly what `_ShelterProbe.enclosure_fraction()`'s existing (if currently ray-based) design already intended: its own doc comment says to pass "the THREAT's blocker layer, not the probing body's own collision_mask." Converted to a radius-parameterized shape-cast ring probe (§8c item 6) and run at a *threat* radius rather than the occupant's own, a high blocked-fraction all the way around is precisely the signal "this pocket walls out something this size" — no mouth concept needed, and it directly produces the `observed`-tier shelter belief (decision 9) at that location. Triggered opportunistically the same way C22's shelter-observation gate already fires (on REST/idle in `creature_motor_stack.gd`), not from any blocked-movement event, since there isn't one to trigger from.

    **Superseded same day by a cleaner split (2026-09-18, second pass) — the "what radius without a real threat" question above is dissolved, not answered, by separating nomination from suitability into two stages:**

    - **Stage A — candidate nomination.** Boolean, evaluated at the **occupant's own radius only**, no threat involved at all: "am I standing in a pocket bounded all the way around, at my own body size?" This is exactly what `_ShelterProbe.enclosure_fraction()`, converted to a shape-cast ring sweep (§8c item 6), computes — just parameterized by the occupant's own known radius, never a threat's. Because no threat radius is ever needed for this stage, **the cold-start question from the first pass doesn't need an answer — it doesn't arise.** Triggered opportunistically (same gate as C22's shelter observation, or during Explore per the user's framing) and mints an `observed` `GK_SHELTER` belief at that point; decision 9's tier lifecycle (`observed`→`confirmed`/`battle_tested`) proceeds from there exactly as already designed, unchanged.
    - **Stage B — per-specific-threat suitability gate.** Boolean, evaluated at the **specific threat's** (held, composure-noised — decision 18/8d) radius, run only at an actual tactical moment (a flee decision, or the STAY-evaluate confirm this decision item originally flagged) — a real threat is always present when this stage runs, so there's no cold-start case here either. Sweep the same boundary at the threat's radius; **any single breach anywhere disqualifies the whole candidate outright** — not a fractional or averaged score. One gap wide enough for the threat defeats the shelter regardless of how solid the rest of the boundary is (user's framing: "even one shrub big enough for the threat to enter makes the shelter an unsuitable candidate"). This is the previously-unspecified mechanism behind decision 20's "fit-gate for squeeze/shelter candidates specifically" — that fit-gate *is* Stage B.
    - Both stages are the same underlying ring-sweep shape-cast primitive, just parameterized by which radius to test (self vs. a specific threat) and by what the result means (a nomination threshold vs. a hard disqualifier) — one function, two call sites, not two separate mechanisms. §8c item 6 is revised to build this shared two-mode sweep rather than a single "high fraction = shelter" measurement.
    - This also confirms decision 12's split stands as corrected earlier today: a uniformly-porous ring has no distinguished mouth and stays entirely in this plain-enclosure mechanism — Stage A/B above **is** the plain-enclosure bucket's full design, not a third bucket layered on top of it.
14. **Wolf reskin — scale up as a real size-differentiated archetype.** Fox has already been reskinned to a wolf visually; scale both the model and the creature profile (`creature_size`, `collision_capsule_radius`, associated mesh/collision) up roughly **3x** relative to fox, to create a genuine size gap for testing/tuning the squeeze mechanic against. This is actionable independent of the tier scheme being finalized (it's tuning one archetype's raw numbers), though final capsule-radius targets may need revisiting once tier boundaries are set.
15. **MobHitbox flagged for review once combat lands** — the predator/prey dichotomy it currently assumes will dissolve once any creature can interact directly with any other (combat, and per user: likely also mating and non-violent resource-sharing). Not in scope now; tracked so it isn't forgotten when combat design starts.
16. **§4a resolved (2026-09-17): query-enforced, not physics-engine-enforced, for everything except layer-1 terrain.** Terrain keeps real physics-layer solidity, unchanged, engine-enforced. For everything else, the motor's own locomotion code decides passability by querying a data model *before* committing a movement step, rather than relying on `move_and_slide`'s automatic collision response — because physics layers are binary per body and can't express continuous, size-relative impact, which is what's wanted for essentially everything that isn't immobile terrain. Two mechanisms, split by geometry shape, both query-enforced:
    - **Object-scale (individual shrubs, boulders, enclosure mouths — anything with a discrete, meaningfully-shaped boundary):** a shared, movement-inert "query-only" physics layer (reusing one of the bits freed by retiring the diet-role split, §3.1) that these objects get a *real* `CollisionShape3D` on, sized/derived from the object's actual model geometry (reusing the mesh-AABB-to-collision-shape derivation `creature_kinematic_body_3d.gd`'s `apply_capsule_footprint_from_visual()` and `bush_food_3d.gd`'s `_sync_mesh_collision_from_visual`/`_StaticObstacleCollision` already do for creatures and bushes respectively — not new machinery). This layer is excluded from every creature's *real* movement `collision_mask`, so it never physically blocks anyone. The motor shape-casts the moving creature's own actual capsule radius against it before allowing a step. This gives exact, continuous, per-instance/per-creature comparison (a real 0.6m rabbit vs. a real 0.7m fox, not "small" vs. "medium" buckets) — **retires the need for discrete size tiers for this purpose**, superseding §4b/§4c as originally framed (see their updated status below).
    - **Field-scale (continuous area effects with no discrete shape to squeeze through — mud, snow, water):** the existing `EnvironmentCellData`/`EnvironmentGridBaked` grid (§2b), unchanged in concept from what's already implemented, just finally wired to something.
    - **Creature-vs-creature** doesn't need the query-only layer at all — each creature already has a real, correctly-sized, always-current body collider (already excluded from every other creature's real movement mask today, confirmed: neither herbivore mask=1 nor carnivore mask=9 includes the other's body layer). A future "can I push past this other creature" check would shape-cast directly against that creature's existing body shape, no separate representation needed.
    - **Overlap/composition rule** (e.g. a shrub rooted in a water cell): reuses `EnvironmentMovementImpact.merge_greatest_impact()`'s existing precedence exactly, just broadened to accept inputs from both mechanisms, not only grid cells. Order: (1) **hard gate first** — any single source saying "you cannot be here" (object shape-cast blocks, or a field cell's own Mode-A) wins outright, regardless of what anything else says; (2) **if the move is allowed, take the single worst continuous `movement_impact` among every source that applies** (object Mode-B slowdown, field cell slowdown, etc.) — **not stacked/multiplicative**. **First-pass decision (2026-09-17):** worst-alone, no compounding, even when an object-scale and a field-scale slowdown coincide at the same point — revisit later if playtesting says standing in *both* effects at once should feel worse than either alone.
    - **Performance note, not a decision:** object-scale shape-casts only need to check nearby colliders (standard broad-phase spatial query), same pattern already used by `_ShelterProbe`/blocked-approach checks — not a full-scene scan per movement step.
17. **§4d resolved (2026-09-17): automatic geometry-derived sizing by default, for now.** Every object gets its query-only collider sized from its actual model geometry (§3 decision 16); no authored-override mechanism is being built yet. If a specific case needs its gap to differ from its visual silhouette later, add that override then — not speculatively now.
18. **§4i resolved (2026-09-17): decision 8 confirmed, and the noisy quantity is a raw size/radius estimate.** Ground truth stays stored; noise applies only at the moment of a real-time tactical decision (decision 8 is no longer tentative). What's actually being estimated at that moment, now that §4a killed tiers and §4g gave a concrete worked example: a raw size/radius value — a stored belief (self's own radius, or a remembered gap's confirmed opening width from a squeeze/shelter belief — see decision 19's 2026-09-18 revision) compared against a live, `stat_composure`-noised estimate of a specific threat's size. Not a tier index (tiers don't exist post-§4a/§4b) and not a grid `fit_size` result (that only governs the unrelated field-scale speed-multiplier case, not a "does this specific threat fit" question).
19. **§4g resolved (2026-09-17): choke-point/squeeze-gap belief model.** A separate belief type from shelter (decision 12), same underlying row-storage machinery (`goal_belief_memory.gd`'s loc-keyed, tiered pattern) but its own bucket and its own tier semantics:
    - **Two-tier evidence model, not three** — `observed` and `confirmed` only. No `battle_tested`: shelter's third tier exists to capture *protective efficacy* (something direct experience alone can't prove), but a squeeze gap's width is a physical fact — walking through it already gives ground truth, no adversarial validation adds anything further.
    - **`observed`**: a distance/angle-estimated guess at the gap's size, noisy, weight scales down with distance/angle at observation time (reuses the composure/observation stat-curve tooling already built for decision 7, just a separate curve instance keyed to `stat_observation` instead of `stat_composure`).
    - **`confirmed`**: set when a creature actually passes through. **Revised (2026-09-18):** stores the **actual geometric opening width** — a real measurement of the gap taken at pass time (e.g. via the same shape-cast/geometry-derived sizing decision 17 already uses for object colliders), not the passer's own radius. This corrects the doc's original framing, which stored the *passer's* known size instead — user recollection was that the actual gap size was always the intended stored value, and storing the true geometric fact is strictly better: it's a physical constant independent of who happens to confirm it (directly resolves §8f's update-policy question — see below), and the inverse/interception use case still works from it: a pursuer compares a fleeing creature's known/estimated size directly against the confirmed opening width ("that thing fits through an opening I know is too narrow for me") rather than against a remembered passer's size, which is a strictly more direct comparison than the original design. Not wired anywhere yet; flagged as a real future consumer of this belief, not a hypothetical.
    - **Ground-truth-vs-noise (this is this belief type's answer to §4i):** `confirmed` is stored as-is, ground truth, no noise applied at storage time. Noise only re-enters at tactical use, when a creature compares a stored gap value (its own confirmed opening width) against its live, composure-noised estimate of a *specific* threat's size — consistent with decision 8's existing default, now concretely instantiated for a second belief type.
    - **Not a goal of its own.** Consulted as a weighted input inside other goals' existing decision points — flee/`GOAL_AVOID_HOSTILES` bearing selection is the obvious consumer (same integration pattern as shelter, decision 10), but explore may also want to weight passing near an `observed`-only squeeze point higher than equivalent open ground, purely to convert it to `confirmed`.
    - **Weighting during flee is a factor, not a binary gate** — combines evidence tier (confirmed outweighs observed) with distance to the point at decision time (a nearby squeeze/shelter should generally outweigh a farther one, and a farther `confirmed` gap can still outweigh a nearer `observed` one, exactly the tradeoff you described). Exact weighting formula is implementation-time detail, not resolved here, but should probably share its shape with shelter's analogous weighting (`shelter_tier_weight` plus a distance term) rather than being invented independently.
    - **Decay reuses the existing generic belief-memory tiering** already implemented in `goal_belief_memory.gd` (precise → coarse/relative → forgotten, `maintain()`), the same mechanism every goal kind already rides on (not something special-cased for food) — just with its own goal-kind-scoped TTL/radius overrides, mirroring the existing `_shelter`-suffixed override pattern (e.g. `goal_memory_ttl_sec_shelter`). `confirmed` rows likely want generous overrides given the value is a durable physical-ish fact; `observed` rows can use tighter/default decay.
    - **Separate storage bucket** — own `goal_kind` (e.g. `GK_CHOKE_POINT`), own table, not shelter's rows. Shelter and squeeze are different mechanics that happen to share row-shape machinery, not one system.
    - **Multi-mouth/tunnel topology is explicitly out of scope for now.** A gap is stored as a single mouth point + radius; a passage with multiple mouths gets each mouth stored independently, with **no recorded relationship between them**. Modeling a real underground-passage/multi-entrance topology is its own design session or later — not needed for the current single-mouth-squeeze and enclosure-with-one-opening cases this doc is actually solving.
    - **Shares its primitive with decision 13's known enclosure-mouth gap** — "can this specific pursuer fit through the shelter's opening" is the same measured/known-size-vs-threat-size comparison, just applied at a shelter's mouth instead of an open-terrain choke point. The mouth is a squeeze belief; what's inside is the shelter belief (decision 12) — same physical object, two different anchor points, two different belief types, already-designed comparison logic reused for both.
20. **§4j resolved (2026-09-17): flee-bias strength and route-clearance mechanics.**
    - **Bonus, not override.** A shelter/squeeze belief adds to a candidate bearing's existing score; it never unconditionally wins over open ground or overrides the base avoid-hostiles scoring.
    - **Race-margin function for route-clearance**, replacing the abandoned navmesh-path-reuse plan: compare the creature's distance to the candidate point against the (nearest relevant) threat's distance to that *same* point — a "who gets there first" proxy. Explicitly **not speed-aware for now** — equal-speed assumption, since real speed/cornering precision is a deliberately deferred future refinement (see below), and a rough proxy is acceptable ("doesn't have to be perfect"). The resulting margin drives the bonus/penalty, monotonically: a clearly-favorable margin → large bonus; a close/uncertain race → smaller bonus (attempting a toss-up isn't punished); a margin suggesting the creature loses the race → bonus drops to zero; a margin that's clearly losing → **negative weight** (actively discourages committing to a path that's already lost, since that both wastes flight distance and can cut off better options). Exact function shape/thresholds (piecewise vs. continuous, where the zero-crossing and "clearly losing" cutoff sit) is implementation-time tuning, not decided here.
    - **Composure-driven size-estimate noise (§3 decision 7) scopes to the fit judgment only** — it decides whether "I fit and the threat doesn't" is judged true/false/uncertain for a given squeeze belief. It does **not** additionally scale the resulting bonus once that judgment is made — no double-application of noise on top of the race-margin math above.
    - **Candidate pool widens, from nearest-shelter-only to a shared radius envelope.** Today's flee scoring evaluates 8 fixed open-field bearings plus one nearest shelter candidate; that changes to: the 8 open-field bearings, plus **every** shelter/squeeze belief within the same radius used for those 8 bearings — all scored through one common function (base avoid-hostiles term + race-margin bonus, + the fit-gate for squeeze/shelter candidates specifically) and compared directly. This is what enables real multi-target blending — e.g. a squeeze that clears one of two pursuing threats but not the other scores according to the *worst* (most dangerous) margin among threats considered, and can end up scoring below clear open ground with no threats nearby, exactly as intended.
    - **Threat aggregation when multiple threats are present**: worst-case margin across all threats currently being considered for avoidance (not summed/averaged) — being caught by any one pursuer is the failure condition, so the most dangerous threat's margin governs. Exact set of "threats currently being considered" reuses whatever the existing avoid-hostiles threat list already tracks each tick, not new bookkeeping.
    - **The same race-margin function generalizes to the 8 open-field bearings too**, not just shelter/squeeze candidates — unifying scoring across the whole candidate pool instead of having shelter/squeeze use one method and open ground another. In the simple single-threat/open-ground case this degenerates to (doesn't conflict with) today's basic "away from threat" distance heuristic — the race triangle collapses toward a line when there's no third point (the squeeze) to reason about.
    - **Explicitly deferred, tracked as future refinement, not in scope now:** incorporating actual creature speed and cornering/turn-rate into the race-margin math for better precision on off-angle approaches. Current math is pure-distance, equal-speed proxy; revisit once/if the coarse version proves insufficient in practice.
21. **§4f resolved (2026-09-17): dead-end handling — shared check subroutine + belief-overlap override.**
    - **One shared subroutine, not a mint-pipeline refactor.** No single common low-level "mint a waypoint" call exists today — `_mint_locale_search_waypoint`, `_mint_explore_objective_for_goal`, `_mint_flee_waypoint`, the C1 pursuit-detour latch, and shelter's own precise-candidate approach are five independent functions. Rather than restructure them into one pipeline, add one shared check function, called identically from each site's own tail — same shape as the `is_waypoint_dead_end` call `motor_explore_seek.gd` already makes today, just with the override folded in. Centralizes the *logic*, not the call graph.
    - **Stays a plain boolean, no new stored attribute.** The subroutine returns a single disqualify/allow result; no `dead_end` field gets added to candidate/waypoint dicts or threaded through state. Keeps the footprint minimal — each mint site just skips/rejects a disqualified candidate and tries another, exactly like explore does today.
    - **Two-step logic:** (1) cheap early-out — run the existing `is_waypoint_dead_end` query (already goal-kind-scoped, bounded to ≤12 marks/creature, 15s TTL); if it's not a known dead end, allow immediately, no further work — this is the common case. (2) Only if it *is* a known dead end, scan known beliefs (any goal kind, any tier — food, shelter, squeeze, anything) for one whose location overlaps the same spot (reuse `dead_end_match_radius` for this overlap radius too, for consistency). Any overlap at all is sufficient to override — **no confidence-tier threshold needed**, which simplifies away the earlier open sub-question about how confident a belief has to be.
    - **Overlap found → allow.** No overlap → disqualify, candidate gets skipped. This generalizes decision 11's flee-to-shelter case for free — a shelter belief's own location typically *is* the dead-end pocket being evaluated, so it already satisfies the override without any goal-specific carve-out.
    - **Performance is a non-issue by construction** — both scans involved are already small, bounded, per-creature lists (≤12 dead-end marks, ~25 belief rows per the existing `goal_memory_max_entries` default), not a scene-wide or spatially-indexed structure. Worst case is on the order of a few hundred comparisons, only on the already-rare "this is a known dead end" branch.
    - **Remaining implementation-time detail, not blocking:** the concrete rollout list of five mint sites above still needs each to actually call the new shared check at its tail — an audit/wiring task, not a further design question.

39. **§9 slice 9 landed (2026-09-21): flee-bias scoring integration (decision 20) — one common scoring function, widened candidate pool, race margin, bonus-only weighting.** Closes the gap the 2026-09-21 "fled instead of sheltering" investigation surfaced.
    - **`FleeCandidateScoring`** (`flee_candidate_scoring.gd`, pure functions) + `MotorPlanner._mint_flee_waypoint` rewired to use it. Every candidate (the 6 open bearings *and* shelter/choke beliefs) is scored `effective = reach + flee_dist × (race_term(margin) + belief_bonus × belief_race_factor(margin))`. As before, only `effective` is biased — `best_reach`/`final_reach` stay the true, unbiased reach, so the RT1/C9/C16/C17 give-up escalation and boxed-in handling are untouched.
    - **Race margin is a scale-free ratio, not distance / flee_dist:** `(d_threat − d_self) / (d_threat + d_self)` per threat, **worst (min) across threats** (never summed/averaged, per decision 20). First draft normalized by the flee distance and was nearly 0 for every nearby candidate (a shelter 10 units away in a 1500-unit-awareness test arena), so a belief's flat bonus swamped it. Equal-speed, pure-distance, as decision 20 specifies.
    - **Bonus curve:** `race_term = clamp(margin, ±cap) × gain` (defaults cap 0.5, gain 0.6): favorable → bonus, dead heat → 0, clearly losing → negative. A belief's own bonus (`flee_shelter_bias_bonus` / `flee_choke_bias_bonus`, × tier weight × proximity) is additionally gated 0..1 by the race (`belief_race_factor`: full when winning, half at a toss-up, zero when clearly losing) — bonus, not override.
    - **Widened pool:** every confirmed-or-better shelter belief (new `MemoryAdapter.consult_shelter_belief_candidates`) and every usable choke belief (`consult_choke_point_beliefs`) within `flee_belief_radius_factor` × flee distance, nearest `flee_belief_max_candidates` (4) kept, replaces the single pre-picked nearest shelter appended as a 7th direction (RT4 Slice 2). A belief candidate is probed only out to the belief itself so the waypoint lands *on* it; its raw reach would then be tiny next to an open bearing's, so it is scored as the fraction of that trip actually reachable × the full flee distance.
    - **Real bug this fixes:** a confirmed shelter *behind* the threat used to win on its flat bonus alone (every bearing ties on reach with no navmesh) and send the creature straight at its pursuer. It now scores below open ground.
    - **Choke fit-check (the squeeze-belief half of decision 20's "fit-gate"):** a choke belief enters the pool only if the creature fits (`opening_width ≥ own diameter`) and every considered threat is *known* not to (`opening_width < threat diameter`); a threat of unknown size disqualifies it.     - **Not in this slice (slice 10):** Stage B ring-sweep fit-gate for *shelter* candidates (a shelter with one threat-sized breach anywhere on its boundary should be disqualified, not merely scored — today shelters get only the race margin), decision 23's live detour-forcing bonus, and noised/held threat-size estimates. Also untested against a live playtest: no navmesh in the unit fixtures, so route-scan truncation interacting with belief candidates is only covered by the existing scan tests. All weights untuned.
    - **Tests:** `_test_flee_candidate_scoring_math` (worst-case aggregation, monotone curve, choke usefulness cases), `_test_motor_planner_flee_ignores_shelter_behind_the_threat`, `_test_motor_planner_flee_pool_prefers_shelter_it_reaches_first`, `_test_motor_planner_flee_choke_belief_needs_fit_gate` (big threat -> chosen; threat that fits, unknown size, or a too-narrow gap -> not). ## 8. Risks, gaps, and trade-offs not yet explicitly decided (review, 2026-09-17)

With §4 fully resolved, a review pass against the actual code (not just the doc) surfaced several things that are either genuine unaddressed gaps or trade-offs the decisions above made implicitly without stating them. ### 8a. ~~Largest gap: NavigationServer3D's single shared navmesh was never reconciled with per-instance passability~~ RESOLVED (2026-09-18)
This is the same problem §1 opened with — "trying to bias flee toward such a spot runs headlong into the shared `NavigationRegion3D`'s bake including all collision layers for every agent regardless of species" — and decision 16 resolves real-time movement collision, but had never revisited navmesh baking. Confirmed in code: `main_3d.gd`'s `_bake_playfield_navmesh()` never sets `geometry_collision_mask`, so it defaults to "all layers" (Godot's own default).

**`geometry_collision_mask` is set to exclude the query-only ghost layer** (bake from layer-1 terrain only, matching decision 16's own split — terrain is the only thing still engine-enforced). The navmesh treats every squeeze gap and object-scale obstacle as open floor for every creature, rabbit or fox alike. This is necessary but, per user instruction, explicitly **not sufficient on its own** — baking the ghost layer into the navmesh at all was rejected outright ("we definitely can't bake the `geometry_collision_mask` into the navmesh"), because a per-species passability fact can't be expressed in a single shared bake regardless of which mask is chosen.

**What replaces "path into a gap, bounce off, replan" as the accepted behavior:** a **route plausibility scan**, run at candidate-scoring time (not discovered mid-flight):

1. For a given desirability candidate (a flee bearing, a shelter/squeeze belief, an explore waypoint — anything scored per decision 20's shared candidate-scoring function), first get the ordinary navmesh path from the creature's current position to the candidate point. Since the bake now excludes the ghost layer, this path always exists in the open-floor sense — it says nothing yet about whether *this* creature can actually use it.
2. Walk that path forward, in path order, and query the ghost/query-only layer (decision 16's object-scale mechanism) for every object collider that intersects the path polyline — not just the first thing encountered, all of them in sequence.
3. At each object in turn, shape-cast the creature's own actual capsule radius against it (the same primitive the live motor step already uses, decision 16 — this scan doesn't invent a second passability check, it just runs the existing one ahead of time along the whole route instead of one step at a time):
   - **Fits** (passable, with or without a Mode-B `movement_impact` slowdown): merge that impact into a running worst-alone accumulator (reuses `merge_greatest_impact()`, decision 16's overlap rule — not stacked/summed across multiple passable objects along the route), and keep scanning past it.
   - **Does not fit** (a real solid-for-this-creature obstacle): stop the scan right there. Everything on the path beyond this point is unreachable via this route for this creature.
4. Feed the scan's outcome into the candidate's desirability score (decision 20's shared scoring function gets a new input term):
   - A scan that reaches the candidate cleanly (no blocker, at most some accumulated slowdown) applies that accumulated impact as a desirability penalty — a route with a squeeze along it scores lower than an equally-close route with none, using the same "worst-alone, not stacked" precedence already established.
   - A scan that hits a real blocker before reaching the candidate **disqualifies the candidate outright** for this route — not a penalty, a removal from consideration, since the creature genuinely cannot get there this way. (A candidate can still be reachable by some *other* route the navmesh would offer if the first one is rejected — this scan operates per-candidate, on whatever path the navmesh actually returns for it, not as a global reachability oracle.)
5. This makes the size-mismatch case a non-event at decision time rather than a runtime failure mode: a fox never *commits* to a bearing or waypoint that routes it through a gap only a rabbit fits, because that candidate was already disqualified before it was chosen. `apply_blocked_objective_resolution`'s existing replan-on-block path is kept, but demoted to a fallback for genuinely dynamic cases the scan can't see ahead of time (e.g. another creature moving into the route after the candidate was already chosen, or a size buff/debuff changing mid-transit) — not the primary mechanism for handling size mismatch, which the scan now prevents from arising in the first place.

**Performance note, not a decision:** this scan is heavier than the live per-step shape-cast (it walks a whole path, not one step), so it should run only when a goal actually needs to (re)score its candidate set (e.g. a flee decision tick, a new explore waypoint mint) — not every physics tick for every candidate already in flight. The existing broad-phase-bounded shape-cast pattern (decision 16's performance note) still applies per object check within the scan.

### 8b. Line-of-sight/occlusion never got reconciled with the layer changes — direction set (2026-09-18), out of scope for this pass
Already self-flagged once in §2b bucket 3 ("worth checking for overlap with the awareness system... not checked this session") but worth resurfacing now that implementation is imminent. Confirmed in code: `line_of_sight.gd`'s occlusion query uses `WORLD_STATIC_MASK := 1` only ([line_of_sight.gd:6](creature/motor/line_of_sight.gd#L6)) — layer 1, nothing else. Today's shrubs (layer 8, or solid_shrub's own layer-1 body) already interact with this inconsistently; under the new model, object-scale obstacles move to a dedicated query-only layer that LOS doesn't check at all. Net effect: a boulder or dense shrub a creature can't physically fit through still won't block *sight* — a threat can be "seen" straight through something it can't walk through.

**Direction set, not designed:** the §8a route plausibility scan is the right mechanism to reuse for vision too, rather than inventing a second per-object traversal — same walk, same per-object query. It likely wants a second per-object property alongside `movement_impact` — a `lineofsight_impact`, how much a given object attenuates/blocks sight through it, independent of whether it's passable (a thin shrub might be easy to squeeze through but still fully block sight, or vice versa) — merged into the existing obscurement math the same way `movement_impact` merges via `merge_greatest_impact()`. **Explicitly out of scope for this implementation pass** — tracked in [ENHANCEMENT_BACKLOG_PLAN.md](../ENHANCEMENT_BACKLOG_PLAN.md) (Perception & awareness) for when LoS/occlusion work is picked up, not blocking the current physics/squeeze work.

### 8d. ~~Trade-off not discussed: continuous per-instance sizing creates a flicker/hysteresis risk that discrete tiers didn't have~~ RESOLVED (2026-09-18)
Decision 16's continuous shape-cast comparison is a real improvement over tiers, but it comes with a cost the doc frames as pure upside: because size is runtime-mutable (decision 5) and every fit judgment is presumably re-evaluated live, a creature near a threshold size (a buff/debuff ticking on/off, or a noisy composure-driven threat-size estimate wobbling near the boundary) could flip between "I fit" and "I don't fit" moment-to-moment. Discrete tiers had this problem too in principle, but continuous values plus live noise make it more likely to land exactly on a knife's edge.

**Resolution: the noisy estimate is rolled once and held as a belief, not re-rolled every tick.** A composure-noised threat-size (or self-fit) judgment is computed once at the moment it's needed, then stored and reused until something concrete invalidates it — it does not silently re-sample every physics tick just because time passed, which is what would cause knife-edge flicker. **A *new* evaluation can still supersede the held belief**, but only when triggered by an actual event that legitimately warrants a fresh read (e.g. distance to the threat/gap changing meaningfully, a new observation, a state transition like flight starting/ending) — not a bare re-roll on a timer. This means a new evaluation can, in principle, produce a *less* accurate estimate than the one it replaces (noise is still noise) — that's an accepted trade-off, not a bug: the alternative (silently keeping a stale-but-luckier estimate) is worse, since it would mean the creature's belief stops tracking reality at all once it happens to land on a favorable roll. Reuses the same held-until-invalidated shape as `observed`/`confirmed`/`battle_tested` belief promotion elsewhere in this doc (decision 9, decision 19) — consistent with how every other belief type in this system already behaves, not a special case invented for this problem.

### 8e. ~~Unaddressed: what happens on interpenetration/edge-case overlap with a purely query-enforced model~~ RESOLVED (2026-09-18)
Real physics collision self-corrects overlap (bodies get pushed apart automatically). A query-only, check-before-you-move model has no equivalent — if a creature ever ends up overlapping a collider it shouldn't fit through (spawn placement, a shrink-then-regrow size buff, another creature shoving it), every proposed step could fail the query with no built-in escape path, a potential soft-lock.

**Answering the load-bearing question first: no, real engine physics does not apply here.** Per decision 16, real `move_and_slide` collision only ever applies to layer-1 terrain — that stays engine-enforced and self-correcting exactly as today, out of scope for this concern. Everything this doc adds (the object-scale ghost layer, decision 16) is deliberately query-only with no physics body backing it, specifically because a static per-body layer/mask can't express continuous per-instance fit. Creature-vs-creature bodies are real physics bodies, but are already mutually excluded from each other's real movement mask today (confirmed in §3 decision 16), so they don't get engine-depenetrated against each other either, now or previously. So the fuzziness-is-fine option isn't available here — this does need its own answer, since nothing else will catch it.

**Resolution: the previously-sketched escape hatch is adopted as the design.** A proposed step is always allowed when it would strictly increase the creature's clearance/distance from the specific shape it's currently overlapping, even if the destination itself would independently fail a fresh fit query — i.e., "getting out" is never blocked by the same check that prevents "getting further in." This is evaluated per offending shape (a creature could be extracting from one overlap while approaching a different, legitimately-solid one) and only engages when an overlap already exists — it doesn't loosen the ordinary pre-commit fit check from §8a's route scan or decision 16's live per-step shape-cast in any case where the creature isn't already stuck. Implementation-time detail, not decided here: the exact clearance comparison (e.g. distance-to-shape-surface increasing tick-over-tick) and how it composes with §8a's route-scan disqualification (an escaping creature's route scan should presumably suppress the disqualification for the shape it's actively escaping, or the escape hatch and the pre-commit filter would fight each other).

**Implemented (2026-09-18), after a live repro made this urgent rather than deferred — see §9 slice 3.** Landed as `GhostObstacleQuery.escaping_overlap()`, using each overlapped collider's own world position as the clearance proxy this entry flagged as an open implementation detail. One deliberate deviation from "strictly increase": the shipped check is **non-decreasing**, not strictly-increasing — a lateral or zero-displacement move also counts as escaping, not just one that measurably gains ground. Reasoning: a strictly-increasing requirement would still block a creature trying to sidestep along a wall it's stuck against (net distance unchanged, but not "pressing further in" either), which defeats the point of the hatch just as thoroughly as no hatch at all. The route-scan composition question raised here is **not yet addressed** — §8a's route scan doesn't know about escape-hatch state at all yet; tracked as a follow-up once both mechanisms have real playtest mileage against each other, not blocking today's fix.

### 8f. ~~Unaddressed: `confirmed` squeeze-belief update policy when multiple different-sized creatures pass the same gap over time~~ RESOLVED (2026-09-18) — dissolved by revising what's stored, not by picking a ratchet policy
Originally: decision 19 stored the *passer's own known size* at confirm time, which raised a real question — what happens on a **second** confirmation of the same belief row by a differently-sized creature? Ratchet to the largest known passer, or overwrite with the most recent one? Either answer has a real failure mode (a stale small ratchet cap, or a regression when a smaller creature passes later).

**Resolution: the question doesn't need an answer, because the premise changed.** Per decision 19's 2026-09-18 revision (see above), `confirmed` now stores the **actual geometric opening width** — a physical fact about the gap itself, not a property of whichever creature happened to walk through it. Two different-sized creatures confirming the same gap are both measuring the *same* underlying value, not reporting two different competing facts, so there's no ratchet-vs-overwrite choice to make: a second confirmation should simply agree with (or, if measurement noise/implementation precision causes small variance, refine toward) the same width, never regress or need capping. This is a case where 8f turned out not to be an independent problem — it was a downstream symptom of storing the wrong quantity, resolved by 8f's own root-cause fix rather than by a policy layered on top.

### 8g. Trade-off not discussed: no shared/herd belief propagation — CONFIRMED FINE FOR NOW (2026-09-18)
Every belief (shelter, squeeze) lives in a creature's own individual `memory_adapter` — nothing here proposes or rules out sharing discoveries between creatures (e.g., a pack, or same-species individuals). That's consistent with the existing architecture and probably the right default, but it's worth naming as a deliberate trade-off rather than an oversight: many individually-dumb creatures will independently rediscover the same squeeze points and shelters over their lifetimes rather than a population "learning" collectively. **User confirmed: fine for now.** Flagging remains in place so it isn't mistaken later for a bug when two same-species creatures behave inconsistently around the same real-world gap — no design work needed unless/until shared cognition becomes a real feature ask.

### 8h. ~~Rollout risk: this touches core per-tick locomotion for every creature, with no staging/rollback story~~ DIRECTION CONFIRMED (2026-09-18): staged slices, tested as we go
Decision 16 replaces engine-enforced collision with motor-owned query logic for nearly everything except terrain — a foundational change to code that runs every physics tick for every creature. **User confirmed: no implementation plan has been discussed yet, and the intent is to build this in slices, testing each one as it lands** — not a single cross-cutting migration. Not fully resolved — the slice boundaries themselves are a proposal, not yet confirmed by the user — but the *direction* (staged, tested incrementally) is locked.

## 9. Implementation slice plan (draft, 2026-09-18)

## 10. Path to a definitive doc

Once §4a-j resolve and are actually implemented and wired (not just designed — this doc's whole reason for existing is that "Completed_Features" previously meant "data model shipped," not "feature works"), produce a `Definitive_Features` doc covering how the game handles size/passability/terrain interaction generally — absorbing/superseding the overlapping claims currently split across this doc, `OBJECT_AVOIDANCE_PLAN.md`, `ENVIRONMENT_MODEL_PLAN.md`, and `PLANT_ECOLOGY_PLAN.md`'s relevant fields.
